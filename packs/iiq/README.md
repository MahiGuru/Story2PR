# IIQ Project Pack

This pack provides all the IdentityIQ-specific content the agent pipeline
kernel needs to run IIQ tickets. Install this pack alongside the kernel
when you want to use the pipeline on the IdentityIQ codebase.

> **Looking for "which `Layer:` triggers which skill?"** See
> `contexts/config/_catalog.md` (auto-generated by the validator from the
> live `pipeline.yaml`). It lists every canonical Layer, its aliases, the
> path_glob, the skills it loads, and the build command — always in sync
> with what the resolver actually does. Regenerate after edits:
> `node contexts/tools/validate.mjs --update-catalog`.

## What's in the pack

### `rules/` — IIQ-specific Tier 1 rules (all `alwaysApply: true`)

| File | Purpose |
|------|---------|
| `iiq-project-scope.mdc` | Tech stack, repo boundary, allowed/forbidden build commands, ticket prefix (`IIQMAG-XXXX`), primary source paths |
| `iiq-file-placement.mdc` | Where new files go — shared vs. feature, module registration, package structure |
| `iiq-naming-conventions.mdc` | File, class, method, variable, and IIQMessages key naming rules |
| `iiq-import-patterns.mdc` | Import, require, and module registration patterns for AngularJS / Angular 18 / Java |

These 4 files merge into your project's `.cursor/rules/` folder at install
time and are loaded into every agent run by Cursor.

### `skills/` — IIQ-specific Tier 2 skills (loaded on demand)

**LLD generator** (Orchestrator, Story Mode):
- `iiq-lld-generator.md` — 25-section LLD template tuned for IIQ stories

**Bug localization** (Explorer, Bug Mode):
- `iiq-bug-localization.md` — router + Step 0 layer detection
- `iiq-bug-localization-frontend.md` — F1-F4 strategies (IIQMessages key search, URL→file resolution, AngularJS/Angular18/ExtJS/XHTML pairing, console error grep, symptom patterns)
- `iiq-bug-localization-backend.md` — B1-B6 strategies (stack trace top-frame, log line grep, REST endpoint lookup, scheduled task/workflow/BeanShell trace, DB symptom → persistence layer)

**Layer coding standards** (Surgeon, per-task via `Layer` field):
- `iiq-java-standards.md` — Backend/Java
- `iiq-rest-api-standards.md` — Backend/REST
- `iiq-angularjs-standards.md` — Frontend/AngularJS
- `iiq-angular18-standards.md` — Frontend/Angular18
- `iiq-extjs-standards.md` — Frontend/ExtJS
- `iiq-xhtml-standards.md` — Frontend/XHTML
- `iiq-accessibility.md` — Accessibility (cross-layer)
- `iiq-test-standards.md` — Tests

These merge into your project's `.cursor/skills/` folder at install time.

### `agents/` — IIQ-specific subagents (invoked at kernel extension points)

The IIQ pack currently ships **no subagents** — the kernel ships the Amender
(wired to `orchestrator_amend_request`) which all packs get for free. The kernel
defines three additional extension points where this pack can plug in subagents
in future releases:

| Extension point | Purpose |
|------|---------|
| `surgeon_pre_task` | Fires before Surgeon implements a task. Useful for: pre-implementation security audits, dependency checks, scope-drift warnings. |
| `surgeon_post_task` | Fires after Surgeon's per-task build passes. Useful for: lightweight code review, snapshot tests, performance gates. |
| `review_post_check` | Fires after Review's AC compliance check. Useful for: license scans, accessibility audits, secrets scans. |

Subagents are **not** auto-loaded like rules or cat-ed like skills. They
are *invoked* by the parent agent at a kernel-defined extension point —
the parent hands control to the subagent, waits for a return verb, and
acts on it.

To add a pack subagent: drop `subagent-iiq-<name>.md` into `packs/iiq/agents/`
and declare it in `pipeline.yaml` under `subagents.<extension_point>:`. Run
`node contexts/tools/validate.mjs` to verify the file-and-declaration
linkage.

These merge into your project's host `agents/` folder (`.cursor/agents/` or
`.claude/agents/`) at install time
alongside the kernel's five primary agents.

## Starter config files (shipped at `contexts/config/`)

Three files ship in `contexts/config/` in the zip as starter templates.
None are read at runtime — they're source material for the install
step only.

- **`contexts/config/pipeline.iiq.yaml`** — the machine config
  for the IIQ pack. Pure YAML, schema v2. Six top-level sections:
  `meta`, `skills` (layer_map, extra_triggers, orchestrator, explorer),
  `subagents`, `builds` (commands, lint, tests, env_checks, forbidden),
  `explorer_paths`, `runtime` (contexts_layout, trigger), and `jira`
  (label automation, default `iiq-agentic-team` label, JIRA prefix
  `IIQMAG-XXXX`). The installer copies it to `contexts/config/pipeline.yaml`
  during install, then preserves your edits across upgrades.

- **`packs/iiq/project-context.iiq.md`** — the prose
  context: stack reminders, team boundaries, active migrations,
  reference implementations, ticket prefix conventions, and
  cross-cutting constraints (browser support, accessibility level,
  perf budgets). Loaded by Orchestrator on every ticket run. The installer
  copies it to `contexts/project-context.md` during install.
  Customize team boundaries and active migrations for your specific
  IIQ team after install.

- **`contexts/config/ticket-input.template.md`** — pre-flight input template.
  Already at its runtime path in the zip, so install leaves it where it
  is. Clone it per ticket when Orchestrator needs extra context:
  `cp contexts/config/ticket-input.template.md contexts/IIQMAG-1234-input.md`

## Install

See the root `README.md` install section for the procedure. In short:
run `npm run install-pipeline -- --project-root <iiq-project>` (or
`npm run install-pipeline:claude -- --project-root <iiq-project>` for
Claude Code). The installer copies this pack's rules/skills/agents into
the host's folder (`.cursor/` or `.claude/`), the example
`pipeline.iiq.yaml` to `pipeline.yaml`, and the example
`project-context.iiq.md` to `project-context.md`.

## Ownership and modifications

Everything in this pack is safe to modify locally. Under the current schema,
the kernel reads all skill filenames from `skills.layer_map`,
`skills.extra_triggers`, `skills.orchestrator.lld_generator`,
and `skills.explorer.bug_*` in `contexts/config/pipeline.yaml`
— not from any hardcoded reference in the kernel or this pack.

If you add a new layer skill (e.g., `iiq-kotlin-standards.md` for a new
Kotlin backend module), drop it in this pack's `skills/` folder AND add
an entry under `skills.layer_map` in your `contexts/config/pipeline.yaml`.
The kernel upgrade mechanism preserves your pack-level edits as long as
you keep them in the pack and not in the kernel folder.

## Pack-author conventions

The kernel resolver (Surgeon Step 0a) is intentionally forgiving — a task
with `Layer: "Backend REST"` or `Layer: "REST"` or `Layer: "Java REST"`
will still resolve to `Backend/REST` as long as those strings appear in
the entry's `aliases:` list. But forgiveness at resolve-time is a safety
net, not the primary contract. A well-authored pack prevents the variance
upstream.

**Convention 1 — canonical layers at LLD-generation time (Priority 3)**

The LLD generator skill in this pack (`iiq-lld-generator.md`) should
constrain the `Layer:` field of every task it emits to one of the canonical
keys in `skills.layer_map`. Orchestrator Phase A0 exposes this list as
`{canonical_layers}` in its context buffer — the generator skill should
reference it as a hard constraint:

> "The `Layer:` field in every task MUST be one of: `{canonical_layers}`.
> No other value is permitted."

This shifts the problem to LLD-generation time, where a loud failure is
cheap (regenerate the LLD) instead of Surgeon-time where a silent
mis-resolve costs a wrong skill load.

**Convention 2 — aliases document human variance, not schema growth**

When a new phrasing shows up ("Services/REST", "Java Backend"), add it to
the existing entry's `aliases:` list. Do not add a new `layer_map` entry
for the new phrasing — two entries pointing at the same skill set is a
duplication bug the validator will flag. Use `aliases:` when the phrasing
is different; use a new entry only when the skills or build command are
genuinely different.

**Convention 3 — every concrete layer declares a `path_glob`**

Strategy A (file-path resolution) is the primary strategy and only works
when layers declare `path_glob`. A layer without `path_glob` can still be
reached via Strategy B (layer-string lookup), but it won't contribute to
automatic full-stack composition. The only layer that should legitimately
omit `path_glob` is one that isn't tied to a directory — e.g., `Test`,
which applies to files anywhere in the repo based on naming, not location.

**Convention 4 — `aliases` list is short and intentional**

3–5 aliases per entry covers ~95% of tech-lead phrasing variance. If a
layer's alias list is growing past 8 entries, that's a signal either the
canonical name is wrong (rename the entry) or the layer is trying to be
two things (split it).
