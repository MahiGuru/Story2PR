How-to guide

Use, extend, and maintain in plain steps

Recipes for the two people who touch the pipeline: the tech lead (one-time setup + extending the pack) and the team member (daily ticket flow). Every section is a short, numbered recipe. For full reference material see Agent Team — Packs & Install and Agent Team — Output.

Roles & responsibilities

Who does what

Tech lead one-time + on-demand

Sets up the pipeline, runs Project Analyzer, maintains the project-map and shared config, extends the pack with new skills/rules/subagents, rotates shared credentials.

  • Install the pipeline into the project
  • Run @project-analyzer.md Analyze project once
  • Commit contexts/project-map.md + contexts/config/*.yaml
  • Edit contexts/project-context.md with team prose context
  • Extend the pack when adding a layer, standard, or subagent
  • Rescan after major refactors
Team member every ticket

Pulls the repo (gets the shared project-map + config), sets up their personal MCP config once, then runs tickets through the pipeline or standalone.

  • Set up personal MCP config once (from sample)
  • Run tickets: @orchestrator.md Work on PROJ-1234
  • Use @explorer / @surgeon / @review / @ship as each gate opens
  • Use standalone triggers for ad-hoc fixes and research
  • Flag in any pack gaps they find (tech lead extends)
The handoff: the tech lead commits contexts/project-map.md, contexts/project-context.md, and contexts/config/*.yaml to the repo. Team members just git pull and start running tickets — no per-developer analysis or config setup required.
Tech lead

One-time setup — four steps

Run once per project. Takes ~15-30 minutes. After this, the team clones the repo and starts working tickets.

1. Install the pipeline

# From the unzipped pipeline release folder
npm run install-pipeline -- --project-root /path/to/your/project --pack myproj

This copies the kernel + pack into your project's .cursor/ and contexts/ folders. For Claude Code use install-pipeline:claude. Full flag reference: Packs & Install.

2. Validate the config

node contexts/tools/validate.mjs

Expects 10 checks to pass. Most common failure: YAML indentation in one of the 5 split files at contexts/config/.

3. Run Project Analyzer (CRITICAL — do this before anyone else)

@project-analyzer.md Analyze project

Takes 5-15 minutes. Scans the entire codebase and produces:

  • contexts/project-map.md — 12-section project catalog (tech stack, shared components, REST endpoints, button intents, i18n, build commands, test frameworks, and more)
  • Auto-populates shared_paths, operation_patterns, i18n, component_naming in the split YAMLs at contexts/config/
If a team member tries to run a ticket before this step, the pipeline halts pre-flight with "project-map.md missing". That's by design — every downstream agent needs this catalog.

4. Edit project-context + commit

# Edit prose context (team boundaries, active migrations, norms)
vim contexts/project-context.md

# Commit everything
git add contexts/project-map.md \
        contexts/project-context.md \
        contexts/config/*.yaml \
        contexts/config/_catalog.md
git commit -m "Agent pipeline: initial setup"
git push

Team members now git pull to get the shared catalog, then set up their personal MCP config (see §MCP setup below).

Team member

Daily ticket flow

Six commands end-to-end. Every agent stops at a gate — nothing happens until you type the next command.

Per-ticket pipeline

@orchestrator.md Work on PROJ-1234       # Phase C gate: Amend / Go / Cancel
@explorer.md Run the explorer            # gate
@surgeon.md Run the surgeon              # gate
@ac-e2e-check.md Demo PROJ-1234          # OPTIONAL · browser AC verification
@review.md Run the review                # or --slim for fast check
@ship.md Ship it                         # commit + PR + JIRA

At Orchestrator's Phase C gate

Go                                       # proceed to Explorer
Amend: <what to change>                  # fires Amender subagent (section-level LLD edits)
Cancel                                   # halt pipeline

Standalone (no ticket)

@explorer.md Research: how does X work?          # codebase research
@surgeon.md Apply: <spec> in <files>              # small fix (≤5 files, ≤150 lines)
@surgeon.md Implement: + bullet ACs              # AC-driven (≤5 ACs)
@review.md Review changes                        # diff-only
@ac-e2e-check.md Demo <URL>                       # ad-hoc browser walk

Flags you'll actually use

FlagWhen to use
--offlineNo MCPs at all · fill contexts/ticket-input.md + attach images
--skip atlassianJIRA is down or token expired · provide ticket via file or inline Context:
--skip figmaDesigns are on your desktop · drag-drop images into chat
— reference: PROJ-100Work a ticket using a prior ticket as a pattern
--slim (Review)Fast integration check · trusts Surgeon's per-task work
If something surprises you: read (1) the agent's halt message — it always names the next command, (2) the Active Context block printed at pre-flight (shows which MCPs were used, which skills loaded), (3) the file the agent just wrote.
Tech lead

Rescan — keep the project-map fresh

The project-map is a snapshot. Major refactors (new module, new framework, restructured folders) invalidate parts of it. Rescan refreshes those parts without redoing the whole scan.

When to rescan

  • New top-level module or framework added
  • Build system changed (added a layer, new build target)
  • Shared components moved to a different folder
  • Agents start reporting drift warnings (e.g., Explorer flags unknown shared paths)

How to rescan

# Full rescan (all 12 sections — ~5-15 min)
@project-analyzer.md Rescan project

# Scoped rescan (just one stack or section)
@project-analyzer.md Rescan Java           # re-scan Java layer only
@project-analyzer.md Rescan AngularJS      # re-scan AngularJS layer
@project-analyzer.md Rescan shared         # re-scan shared_paths
@project-analyzer.md Rescan build          # re-scan build system + commands
@project-analyzer.md Rescan templates      # re-scan template/layout inheritance
@project-analyzer.md Rescan tests          # re-scan test directories
@project-analyzer.md Rescan stack          # re-scan tech stack detection

The analyzer auto-offers a Rescan menu at the end of each scan showing exactly which scoped rescans are likely relevant next. Run @project-analyzer.md without a verb to see the menu.

Configure rescan hints (in pipeline config)

Edit contexts/config/pipeline.myproj.analyzer.yaml to tune rescan behavior:

rescan_hints:
  # When Orchestrator should suggest a rescan before working a ticket
  freshness_check:
    enabled: true
    min_files_to_check: 3        # skip check if ticket references < N files
    max_age_days: 30             # warn if project-map older than this

  # Which paths trigger which scoped rescan
  triggers:
    - path_pattern: "pom.xml"
      suggest: "Rescan build"
      reason: "build config changed"
    - path_pattern: "package.json"
      suggest: "Rescan build"
    - path_pattern: "src/web/shared/**"
      suggest: "Rescan shared"
    - path_pattern: "src/**/*.java"
      suggest: "Rescan Java"
      threshold: 50              # only if > 50 Java files changed

Commit the refreshed map

git add contexts/project-map.md contexts/config/*.yaml
git commit -m "Rescan: add <what>"
git push
# Team members git pull → get the refreshed map
Tech lead

Extend: add a skill

Skills are per-layer coding standards (e.g., Java, AngularJS, Angular18). Add a skill when a new layer or framework joins the project.

  1. Create the skill file at packs/myproj/skills/myproj-<layer>-standards.md: 
    ---
name: myproj-mynewlayer-standards
description: Coding standards for <layer description>
---
# <Layer> Standards

## Naming
... your rules ...

## File placement
...

## Common patterns
...
  2. Wire it into the layer_map at contexts/config/pipeline.myproj.skills.yaml: 
    skills:
  layer_map:
    Frontend/MyNewLayer:
      path_glob: "src/web/mynewlayer/**/*.ts"
      aliases: [mynewlayer, my-new-layer, MNL]
      skills: [myproj-mynewlayer-standards]
      build: build-mynewlayer
  3. Re-install so the skill lands in .cursor/skills/: 
    npm run install-pipeline -- --project-root /path/to/project --pack myproj --merge-config
  4. Validate + regenerate catalog: 
    node contexts/tools/validate.mjs --update-catalog
# _catalog.md now shows the new layer + resolved skill
  5. Commit: 
    git add packs/myproj/skills/myproj-mynewlayer-standards.md
git add contexts/config/pipeline.myproj.skills.yaml contexts/config/_catalog.md
git commit -m "Add MyNewLayer coding standards"
Where it shows up at runtime: when Surgeon works a task whose file path matches the path_glob OR whose Layer: field matches an alias, it loads myproj-mynewlayer-standards.md into its context. The skill is NOT loaded for tasks outside this layer — on-demand, per-task.
Tech lead

Extend: add a rule (always-on)

Rules are project standards auto-injected into every agent run (via alwaysApply: true). Use a rule for things that should hold project-wide: naming, forbidden patterns, placement rules.

  1. Create the rule file at packs/myproj/rules/myproj-<name>.mdc: 
    ---
description: One-line summary shown to agents
alwaysApply: true
---
# <Rule title>

## What to do
...

## What NOT to do
...

## Examples
...
  2. Re-install: 
    npm run install-pipeline -- --project-root /path/to/project --pack myproj --merge-config
# Installer copies it to .cursor/rules/ (and .claude/rules/ if that host is installed)
# For Claude Code the .mdc is renamed to .md and alwaysApply is stripped
  3. Validate: 
    node contexts/tools/validate.mjs
  4. Commit: 
    git add packs/myproj/rules/myproj-<name>.mdc .cursor/rules/
git commit -m "Rule: <summary>"
Scope: rules apply to EVERY agent, EVERY run — so they should be genuinely universal (project-wide conventions, safety constraints, never-do patterns). Per-layer or per-phase guidance belongs in a skill, not a rule.
Tech lead

Extend: add a subagent (extension point)

Subagents are delegated workers that fire at specific points in the pipeline. Use when you want heavy intermediate work (e.g., security scan, license check) to stay out of the parent agent's context.

Four extension points

Extension pointFires whenTypical uses
orchestrator_amend_requestUser types Amend: at Phase C gateKernel ships Amender here — rarely overridden
surgeon_pre_taskBefore Surgeon starts a code changeSecurity pre-check, scope-drift warning, dependency check
surgeon_post_taskAfter per-task lint + tests passSnapshot tests, performance gate, secrets scan
review_post_checkAfter Review's AC compliance checkLicense audit, accessibility scan, compliance check

How to add one

  1. Create the subagent prompt at packs/myproj/agents/subagent-myproj-<name>.md: 
    ---
name: myproj-security-scan
description: Pack subagent — scans staged changes for secrets / PII at surgeon_post_task
---
# Body: what the subagent reads, what it does, which return verbs it uses
...
  2. Declare it in the pack seed at packs/myproj/pipeline.myproj.yaml (core section): 
    subagents:
  surgeon_post_task:
    - name: myproj-security-scan
      agent: subagent-myproj-security-scan
      when: "task touches src/web/** OR task touches src/api/**"
      # 'when' is free-form; Surgeon parses it to decide whether to invoke
  3. Re-install: 
    npm run install-pipeline -- --project-root /path/to/project --pack myproj --merge-config
  4. Validate: 
    node contexts/tools/validate.mjs
# Checks: subagent file exists + reference in pipeline.yaml matches
  5. Commit: 
    git add packs/myproj/agents/subagent-myproj-<name>.md \
        packs/myproj/pipeline.myproj.yaml .cursor/agents/
git commit -m "Subagent: <summary>"
Skill or subagent? Use a skill when the work IS part of the parent agent's main job (applying coding standards). Use a subagent when the work has heavy intermediate data the parent doesn't need (license scan output, image bytes) and a small structured return is enough.
Tech lead · stack change

Create a new pack (different stack)

A pack bundles all the project-specific knowledge for one stack. Create a new pack when the pipeline should run on a different tech stack (e.g., a Python/Django project vs. a Java/Spring project).

  1. Copy the reference pack: 
    cp -r packs/myproj packs/mystack
cd packs/mystack
  2. Rename the config + skill/rule files: 
    # Rename the seed YAML
mv pipeline.myproj.yaml pipeline.mystack.yaml

# Rename the context template
mv project-context.myproj.md project-context.mystack.md

# Rename the readme
mv pipeline.myproj.readme.md pipeline.mystack.readme.md

# Rename skills (iterative — one per file)
for f in skills/myproj-*.md; do
  mv "$f" "${f/myproj-/mystack-}"
done

# Same for rules
for f in rules/myproj-*.mdc; do
  mv "$f" "${f/myproj-/mystack-}"
done
  3. Update the meta.pack in the seed: 
    # packs/mystack/pipeline.mystack.yaml
meta:
  schema_version: 4
  pack: mystack                   # ← was 'myproj'

# Then update every skills: reference from 'myproj-*' to 'mystack-*':
skills:
  orchestrator:
    lld_generator: mystack-lld-generator.md
    ticket_schema_story: mystack-ticket-schema-story.md
    ac_templates_intent_aware: mystack-ac-templates-intent-aware.md
  layer_map:
    Backend/Python:
      skills: [mystack-python-standards]
    # ... etc
  4. Replace stack-specific content in the skill files:
    • skills/mystack-lld-generator.md — shape the LLD template for your stack
    • skills/mystack-<layer>-standards.md — rewrite per-layer standards
    • skills/mystack-bug-localization-<frontend|backend>.md — localize bug strategies
    • skills/mystack-ticket-schema-<story|bug>.md — match your JIRA custom fields
    • rules/mystack-*.mdc — rewrite naming/placement/imports for your stack
  5. Install into a fresh test project: 
    npm run install-pipeline -- --project-root /path/to/testproject --pack mystack
node contexts/tools/validate.mjs
  6. Run Project Analyzer on the new project to fill in shared_paths, operation_patterns, i18n: 
    @project-analyzer.md Analyze project
Keep the reference pack intact. Don't delete packs/myproj/ — keep it as the worked example. New packs can always diff against it to see how a pack is supposed to be shaped.

MCP setup — per-developer

The installer writes contexts/config/mcp.sample.json + a per-host setup README. Each developer copies entries into their personal Cursor / Claude Code MCP config. Tokens are personal — never commit them.

First-time connect (do once)

  1. Open the sample: 
    cat contexts/config/mcp.sample.json
cat contexts/config/mcp.sample.README.md   # per-host paths + OAuth steps
  2. Atlassian (OAuth — browser):
    • Copy the Atlassian block from mcp.sample.json into your personal Cursor / Claude Code MCP config
    • Trigger OAuth flow in your IDE — browser opens, you approve
    • Token stored in your personal config · valid until it expires
  3. GitHub (personal access token):
    • Create a PAT at github.com → Settings → Developer settings (scope: repo)
    • Paste into the GITHUB_TOKEN placeholder in the sample, copy to your personal config
  4. Figma (personal access token, optional):
    • Create a PAT in Figma → Settings → Personal access tokens
    • Paste into the FIGMA_TOKEN placeholder, copy to your personal config
  5. Test: 
    @orchestrator.md Work on PROJ-1234
# Active Context block should show: atlassian ✓ · github ✓ · figma ✓

Rotate an expired token

  1. Update the token in your personal MCP config
  2. If you were mid-ticket when it expired, Orchestrator's recovery gate offers retry — type it
  3. If you have no open gate, just trigger the next agent normally

Add a new MCP to the pack

If your project needs a new MCP (e.g., a custom internal service MCP), declare it in the pack seed:

# packs/myproj/pipeline.myproj.yaml
mcp_servers:
  myservice:
    auth: token
    config:
      command: "npx"
      args: ["-y", "mcp-server-myservice"]
      env:
        MYSERVICE_TOKEN: "${MYSERVICE_TOKEN}"
    setup_hint: "How developers configure this MCP in their host."

Re-install + run node contexts/tools/mcp-sample-generator.mjs to regenerate mcp.sample.json with the new entry.

Rewire roles — swap an MCP without touching prompts

mcp_roles maps four mandatory roles to concrete MCPs. Change the mapping → agents route differently on the next run. No kernel changes.

  1. Edit mcp_roles in the pack seed: 
    # pipeline.myproj.yaml (core) — alongside mcp_servers
mcp_roles:
  story_source: atlassian              # where tickets live
  design_source: figma                 # where designs live
  vcs: [bitbucket, github]             # primary + fallback
  docs_source: atlassian               # HLDs / wiki

mcp_guidance: {}                        # optional prose quirks
  2. Validate: 
    node contexts/tools/validate.mjs
  3. Re-install + each developer connects the new MCP in their personal host config.
  4. Test: trigger a ticket. Active Context block shows the new routing: 
    Routing:
  story_source  → atlassian ✓
  design_source → figma ✓
  vcs           → bitbucket ✓  (fallback: github unused)
  docs_source   → atlassian ✓
CLI-level caveat: swapping vcs to Bitbucket is a config change, but Ship's PR-create step uses the gh CLI by default. For non-GitHub VCS, install the matching CLI (glab, bb, etc.) and override Ship's push_and_pr step in a pack rule. The routing decision is abstracted; the tooling isn't — yet.
Privacy: no MCP = graceful fallback. Use --offline when content is sensitive. Use --skip <name> to selectively bypass an MCP for one run.

Troubleshooting cheatsheet

SymptomFix
No context file found for PROJ-1234A downstream agent ran before Orchestrator. Start with @orchestrator.md Work on PROJ-1234.
project-map.md missing at pre-flightTech lead hasn't run Project Analyzer yet. Ask them — or if you're the tech lead, run @project-analyzer.md Analyze project.
Ambiguous context file for PROJ-1234Same ticket ID exists in two folders. Move one to contexts/archive/.
skill_loaded=<none — no config>A split YAML failed to parse. Run node contexts/tools/validate.mjs — it names the file + line.
top-level key 'X' declared in multiple filesSame key appears in two split YAMLs. Each block lives in exactly one file — see Pack & Install → Config splits.
Plain trigger didn't route in CursorUse the @<agent>.md <trigger> form. Cursor's router is probabilistic; the @-prefix is reliable.
Surgeon halted with LLD drift warningAmender ran between Surgeon runs. Choose Restart / Proceed / Cancel at the prompt.
Atlassian MCP gate appears mid-runToken expired. Fix your MCP config, then answer retry — or use inline + Context: / file + ticket-input.md.
Figma MCP gate appears mid-runAnswer retry, or upload + drag-drop images + continue, or skip (URL-only visual spec).
Review says "clean" but the code looks brokenReview checks AC compliance + regressions, not behavioral correctness. LLD may be wrong — amend from the top.
Amend: option missing at Phase C gateAmender subagent wasn't installed. Re-run the installer.
Rescan not picking up new filesVerify scan_exclusions in pipeline.myproj.analyzer.yaml isn't excluding the new folder.
Layer resolution picked the wrong skillRun node contexts/tools/validate.mjs --update-catalog and check contexts/config/_catalog.md. Adjust path_glob or aliases to disambiguate.
Debugging sequence: (1) read the agent prompt at .cursor/agents/<name>.md, (2) read the skill it loaded (listed in the Active Context block), (3) read the config section it consumed at contexts/config/pipeline.*.yaml. The answer is always in one of those three places.
