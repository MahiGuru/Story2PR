Executive briefing

The problem

Shipping a single story takes hours of context-switching

Each story pulls a developer through the same motions: read the ticket, hunt through the codebase for similar work, decide what to reuse, write code, run builds, review diffs, raise the PR. Much of that is repeatable. Almost none of it is reused.

What costs us time today

  • Context rebuilt from scratch every ticket. Project knowledge (shared components, endpoints, conventions) lives only in senior heads.
  • Similar stories diverge in implementation. Two developers fix parallel tickets in incompatible ways; code review catches some, not all.
  • AI coding tools are either too autonomous or too generic. They either ship without review or they don't know our stack's conventions.
  • No audit trail. "Why was this built this way?" has no answer beyond a 2-line commit message.
  • Build output floods the chat. When a developer pairs with an AI, every build run burns thousands of tokens and slows the next interaction.

What we want instead

  • Project knowledge captured once, applied consistently across every story by every developer.
  • The developer controls every step. AI does the repeatable work; human approves at every gate.
  • A written record at every stage — design, exploration, implementation, review — committed alongside the code.
  • Tight cost control. Agents read only what they need; build output stays on disk, not in the conversation.
  • Stack-portable. Works on our Java project today, can be swapped to a new stack tomorrow without rewriting the engine.
The solution

A gated agent pipeline — one command starts, six gates deliver a PR

Seven AI agents collaborate through a staged pipeline. Each agent has one job, reads the previous agent's output from disk, produces its own artifact, and hands off through a user-approval gate. No agent proceeds without explicit human authorization.

Specialization

Each agent has a narrow role — planning, exploring, implementing, verifying, reviewing, shipping. Narrow roles stay focused; no one agent tries to do everything.

Developer-gated

Six approval gates, one per stage. The developer reviews each artifact and types the next command — nothing runs autonomously for hours.

Artifact-driven

Every stage writes its output to a file committed with the code. Day-2 resume is free — the next agent reads the file, not a chat history.

Project-aware

Project Analyzer scans the codebase once; the resulting catalog informs every downstream agent — on every ticket, for every developer, consistently.

Auditable

Every decision — the LLD, exploration notes, code manifest, review verdict, build reports — is a file in the PR. Reviewable, searchable, historically accurate.

Dual-host - Inprogress

The same pipeline runs in Cursor and Claude Code. Developers choose their tool; the pipeline doesn't lock us into one vendor.

The developer types @orchestrator.md Work on PROJ-1234 — then types a short approval at each gate (Go, Proceed, Fix, Ship it), or Amend: <text> when something needs a change. No other complex commands required.
Total time from kick-off to PR on the PROJ-1234 walkthrough above: ~90 minutes. The developer spent this time reviewing and approving — not writing code, not searching the codebase, not running builds. The same story without the pipeline typically takes 3–6 hours of active work plus context-switching. Quality becomes consistent across developers because every ticket goes through the same gated flow.
How context scales across an epic

One epic, many stories — context stays compact automatically

A 15-story epic doesn't mean every story pays for 15 stories' worth of reading. The pipeline keeps an epic-context.md file per epic — a compact running ledger of what every prior story built, decided, and discovered. Each new story reads one small file instead of hunting across 15 JIRA tickets, 15 Confluence pages, and the whole codebase. Token cost stays flat; insight grows linearly.

The three context sources for every story

When a developer types Work on PROJ-1234, the Orchestrator pulls context from three places — but only the parts that actually matter for this story. Nothing is re-fetched that already lives in local files.

📁 epic-context.md — the ledger

One file per epic. Contains a coverage header ("9 of 13 stories · 1 HLD · 2 spike docs · drift in sync") plus a compact row for every sibling with Files created / modified · pattern used · decisions · what's reusable. Every row is capped at ~300 tokens — the pipeline writes it, the pipeline reads it back.

Read cost for story 15: ~5K tokens total (all 14 siblings).

📐 project-context.md — the standards

Stack, shared components, conventions, build commands — the one-time answer to "how does this project work?" Loaded on every run; refreshed by a separate analyzer agent when the codebase changes materially.

Read cost: ~2-3K tokens, stable across all stories.

🎯 This story's ticket — the ask

JIRA ticket description + acceptance criteria, Confluence HLD (linked once), Figma design (if attached). The only content fetched fresh per story — everything else is reused from local files.

Read cost: ~3-5K tokens, varies by ticket size.

How sibling-story context gets pulled in

When a sibling story isn't in epic-context (it shipped via a regular PR, or was started outside the pipeline), a lightweight drift check catches it. The pipeline doesn't read every sibling's full design doc — it sorts siblings by JIRA status and applies different strategies per bucket. "Is the content stable enough to read, or is it still churning?" is the question that decides.

Cost benefits

Traditional AI vs the pipeline — cost per story, across the epic

Traditional chat-based AI re-pastes HLD + sibling LLDs + code into every turn, so cost grows story after story. The pipeline carries context in files, so cost stays flat. Same 15 stories, same work, very different bills — the table below shows the divergence. Numbers at Claude Sonnet API pricing, medium story throughout.

💬 Traditional AI usage

Developer chats with AI. No memory between sessions.

  • Re-pastes ticket + HLD + siblings into every chat
  • Each turn re-sends the bloated context again
  • Story 10 burns ~500K tokens in a single chat
  • Story 15 bursts past 1M on retries
📁 Pipeline (artifact-driven)

Agents write to files; next agent reads only its slice.

  • Epic-context.md holds every sibling as a ~300-token summary
  • No re-pasting — pipeline reads what it wrote before
  • Cost stays flat at ~80K tokens per story
  • No context burst, no missed siblings, no HLD drift

How epic-context.md saves tokens — per agent, per story

The savings aren't magic — each pipeline agent reads the epic-context.md ledger instead of re-loading the HLD, sibling LLDs, and the codebase from scratch. Here's what each agent skips on every story after the first.

🧭 Orchestrator

Caches HLD + every shipped sibling as 300-token summaries.

  • Without it: re-reads HLD (~15K) + every sibling LLD (~3K each) every story
  • With epic-context: ~3K cached read, regardless of how many siblings shipped
  • Saves ~25K on story 2 → ~470K on story 15
🔍 Explorer

Caches the epic codebase map — components, hooks, directives already created.

  • Without it: full repo scan (~50K) every single story
  • With cache: incremental delta only (~8K) — just what changed since last story
  • Saves ~40K flat per story · ~560K across the epic
✅ Review

Reuses prior verdicts, AC compliance map, and blast-radius baseline.

  • Without it: re-runs cross-story regression check against every sibling
  • With epic-context: pulls the diff slice + cached test results — verifies, doesn't re-derive
  • Saves ~5K on story 2 → ~230K on story 15

Surgeon and Ship are task-scoped (one slice in, one PR out) — they don't accumulate epic context, so their per-story cost is already flat. The savings below come from the three agents above.

Risks eliminated — not just token savings

No context burst

Each agent runs in a fresh context with only the files it needs. No silent dropping of older content when a chat hits its limit.

No missed siblings or HLD

Drift check catches 100% of JIRA siblings automatically. HLD is auto-fetched and cached in epic-context — no human memory needed.

No cross-story divergence

Every shipped story's pattern + decisions live in epic-context.md. Story 8 sees story 7's choices before any code is written.

The business case is time, not tokens. $12–20 per developer per month is roughly one engineering hour of saved time per week. Saving 30 minutes per story across a 40-story month = 10×+ ROI. API cost is the small line item; time savings and eliminated risks are the real win.

Flexible usage

Beyond the main pipeline — standalone fixes, MCP integrations, offline mode

Not every change needs the full 5-stage flow, and the pipeline plugs into the tools the team already uses. Three modes of flexibility: single-agent standalone runs, MCP integrations for JIRA / GitHub / Figma, and selective or full offline operation for sensitive work.

Standalone mode — one agent, no ticket

For quick fixes and research that don't need a JIRA ticket or the full pipeline. Same agents, single-stage invocation.

Research

@explorer.md Research: <question>
Codebase research on a specific question. No code written — produces a scoped exploration report.

Small fix

@surgeon.md Apply: <spec> in <files>
Targeted change, capped at ≤5 files / ≤150 lines. Over-cap halts with "use pipeline instead".

AC-driven fix

@surgeon.md Implement: + bullet ACs
Implements from a bullet list of acceptance criteria (≤5 ACs). No ticket required.

Quick review

@review.md Review changes
Spot-check the current git diff for code quality — no ticket context, no AC compliance, just a diff review.

Ticket review

@review.md Review PROJ-1234
AC coverage review against an existing ticket — useful when someone else wrote the code and you want a compliance check.

Browser demo

@ac-e2e-check.md Demo <URL>
Ad-hoc browser walkthrough of a page. Captures screenshots and behavior notes without a formal AC list.

MCP integrations — connect to the tools you already use

Fully customizable — any number of MCPs can be declared in the pack config and wired to specific agents. The three below are the starter integrations the reference pack ships; teams add more as their workflow demands (internal service MCPs, custom data sources, deployment tooling, observability, etc.). Each developer sets them up once in their personal Cursor / Claude Code MCP config — the installer ships a starter template generated from whatever the pack declared.

📋 Atlassian — JIRA + Confluence

Orchestrator auto-fetches the JIRA ticket (description, ACs, attachments), reads the Confluence HLD, discovers sibling stories and reference tickets. Ship transitions the ticket on PR open.

OAuth browser flow · personal per developer.

🔗 GitHub — code + PRs

Ship creates the PR with the build-verdict table, AC compliance summary, and blast radius. Review fetches reference tickets' merged PRs for pattern comparison. Explorer can span multiple repositories.

Personal access token (repo scope).

🎨 Figma — designs

Orchestrator fetches structured frame data from Figma URLs in the ticket description (component tree, spacing, states, copy). Image-analysis subagent converts it to a compact visual spec used by the LLD.

Personal access token · optional, falls back to drag-drop images.

➕ Add your own — unlimited

Any MCP server can be declared in the pack config and wired to specific agents. Examples teams have added: internal service MCPs, deployment orchestration, observability / metrics, security scanning, internal wikis, custom data sources.

Declare in pipeline.<pack>.yaml → installer regenerates the starter MCP template automatically.

Connection is per-developer, not team-wide. Each developer copies the starter MCP config from contexts/config/mcp.sample.json into their personal Cursor or Claude Code config and completes the OAuth / token steps once. The pack itself declares which MCPs exist (and which agents use them); credentials stay personal.

Skip / offline — privacy and resilience

Any MCP can be bypassed per-run. Use when content is sensitive, when an MCP is flaking, or when you're simply offline.

--offline

Skip ALL MCPs. Fully local — no network calls to any external service. Provide ticket content via contexts/ticket-input.md + drag-drop images.

--skip atlassian

Skip JIRA / Confluence only. Keep GitHub + Figma. Useful when the JIRA ticket is sensitive or Atlassian is down. Provide ticket content locally.

--skip figma

Skip Figma only. Keep Atlassian + GitHub. Useful when designs are on your desktop or Figma is unavailable — drag-drop images into chat instead.

--only github

Use ONLY GitHub — skip Atlassian and Figma. Useful for tickets where the primary reference is a prior PR and nothing else matters.

Inline Context:

Paste ticket content directly into the trigger message. No file edit needed. Useful for quick one-off runs.

Runtime recovery gate

If an MCP fails mid-run (token expired, timeout), Orchestrator opens an inline gate: retry / inline / file / skip / cancel. Handle it in the same conversation — no abort + re-trigger.

Zero-MCP mode still works. The pipeline was designed so every MCP is optional. With --offline and a local ticket-input.md, every agent in the pipeline still runs — just reading from local files instead of remote services. Sensitive projects and air-gapped environments are supported out of the box.
Team impact

What changes for the team

Tech leads

Set up once, maintain occasionally. Install takes an hour. Running Project Analyzer takes 15 minutes. Extending the pack (adding a new coding standard, a new subagent) is a 3-step recipe. No daily involvement required.

Developers

Less repetitive work, more judgment calls. Developers spend less time hunting for existing code and more time reviewing proposed approaches. The gate-driven flow means they stay in control — AI doesn't ship anything without approval.

Reviewers

Walk into a cleaner PR. AC compliance, blast radius, build verdicts, test coverage — all pre-computed. Review becomes a judgment exercise on the changes, not a forensic exercise on whether things were done correctly.

New hires

Ramp up faster. The project catalog captures the tribal knowledge that usually takes weeks to absorb. New developers run their first ticket through the pipeline on day 2 — and the code follows team conventions from the first PR.

Managers

Better visibility. Every ticket leaves a trail: design rationale, exploration notes, build verdicts. Estimating, retrospecting, and incident post-mortems all get better primary-source material.

Security / compliance

Forbidden-patterns list is centrally enforced. Rules like "never push to main", "no deploy commands from agents", "block secrets patterns" are declared once and applied to every agent run, automatically.
