A staged, artifact-driven pipeline: 1 setup agent + 5 story agents + 2 subagents work your ticket through plan → explore → implement → verify → review → ship. Architecture

How the pipeline works

A staged, artifact-driven pipeline. Each agent runs in its own short-lived conversation, reads inputs from disk, writes outputs to disk, and exits. The user is the scheduler — typing the next agent IS the gate. Day-2 resume is free: any agent can pick up where the prior one left off because state lives in files (LLD, codebase map, manifest, build reports), not in chat history.

Pipeline shape

Step 0   project-analyzer   → contexts/project-map.md          (one-time + on-demand rescans)
Step 1   orchestrator       → 3-file LLD + branch              (Phase C gate · Amend / Go)
            ↓ Amender subagent fires only if user picks Amend
Step 2   explorer           → exploration + codebase-map sync
Step 3   surgeon            → code + manifest                  (per-task loop)
Step 3.5 ac-e2e-check       → browser AC verdicts              (OPTIONAL)
Step 4   review             → review report + epic-context append
Step 5   ship               → commit + PR + JIRA transitions

No agent does anything without your explicit command. No agent commits except Ship.

Pipeline flow — 7 agents + 2 subagents · always-on rules + on-demand skills · user-gated
Every gate shows: progress indicator ([step X/5] DONE), summary metrics, and a highlighted > 👉 Pick one: next-action block with copy-paste-ready commands. Rule: Each gate shows ONLY the immediate next action — never future steps. After every user interaction (fix, skip, verify), the gate MUST re-display with updated state.
Get started

Install, validate, run

Dual-host: same kernel works in Cursor and Claude Code. Pack-driven: project-specific standards live in a swappable pack.

Install

# From the unzipped release folder
npm run install-pipeline -- --project-root /path/to/project --pack yourproj

# Validate
node contexts/tools/validate.mjs   # expects 10 checks pass

The installer copies the kernel to .cursor/ (or Claude Code equivalent), splits the pack's monolithic YAML into 5 per-agent files at contexts/config/, and drops mcp.sample.json for each developer's personal MCP setup.

Kernel + Project Pack

The kernel is project-neutral; packs add stack-specific knowledge

The kernel agent prompts use placeholders ({TICKET_ID}, {frontend_path}, {pack}-...) — zero references to any specific stack. Packs supply the LLD generator skill, layer coding-standards skills, and pipeline.{pack}.yaml. Swap packs to use the same pipeline on a new project.

Kernel ships

7 agent prompts, 2 subagents, agent-flow.mdc always-on rules, kernel skill index, install/validate tooling, generic templates. Project-agnostic.

Pack ships

LLD generator skill, AC-templates skill, ticket-schema skill, per-layer coding-standards skills, pipeline.{pack}.yaml + 4 split companions, pack-specific .mdc rules, pack subagents (optional).

Skills (Tier 2)

Reference material loaded on-demand by an agent into its OWN context. Skill = "how I do my own job." Examples: LLD generator, layer coding standards, AC templates.

Subagents

Delegated workers invoked at extension points. Subagent = "do this for me, give me a small result back." Kernel ships Amender + Image-Analysis. 4 extension points: orchestrator_amend_request, surgeon_pre_task, surgeon_post_task, review_post_check.

Why LLD-generator is a skill, not a subagent

The LLD is Orchestrator's primary job — not a side task. All inputs (ticket schema, AC registry, Requirement Summary, image visual_spec) already live in Orchestrator's context. The output must come back to Orchestrator's context for the Phase C gate anyway. Delegating would cost ~4× more tokens with zero isolation benefit.

Project Analyzer — key capabilities

One-time then on-demand

Runs once at project onboarding (5–15 min). Re-runs incrementally via Rescan <stack> after major refactors. Output is cached in project-map.md and consumed by every other agent.

12 sections of project knowledge

Tech stack, folder map, shared UI components, promotion candidates (3+ uses), backend services, REST endpoints, configs, build system, test frameworks, button intents, i18n, rescan log.

Auto-populates split YAMLs

Discovers shared_paths + component_naming → writes to analyzer.yaml. Discovers operation_patterns + i18n → writes to builds.yaml. No manual config copy-paste.

Build consumer graph

Phase 10 links FE files → REST endpoints → services → DAOs → DB tables. Surgeon and Review use the stack trace to know "this endpoint is consumed by 3 features in 2 frontend stacks."

Orchestrator — key capabilities

Mode auto-detection

Reads JIRA issuetype + parent link → routes to Story / Standalone Bug / Sub-Bug. Each mode has its own synthesis flow but produces the same 4-part shape downstream agents expect.

Three-file LLD split

Writes $CONTEXTS_FILE (Requirement Summary + ACs), $LLD_FILE (PART 1 Design + PART 2 Tasks), $TESTPLAN_FILE (PART 3 Test Plan + PART 4 Test Tasks). Downstream agents load only the file they need.

MCP-driven enrichment

Atlassian MCP auto-discovers reference tickets via jira.reference_link_types + JIRA image attachments. Figma MCP fetches structured frame data from URLs. GitHub MCP inspects reference PRs. All graceful — no MCP = standard run.

Image-analysis subagent

Spawns subagent-image-analysis for raw image bytes (15-25K tokens). Returns compact {visual_spec}. Raw bytes never enter Orchestrator's context.

Phase C gate · Amend / Go

User reviews LLD summary. Amend: <text> spawns the kernel Amender subagent for targeted section-level edits — ~6× cheaper than re-running Orchestrator.

LLD generator as skill

Pack-supplied {pack}-lld-generator.md loaded only at Phase B. Pack-swappable. Cheaper than a subagent because all inputs already live in Orchestrator's context.

Offline + selective MCP

--offline skips all MCPs. --skip atlassian,figma selective. --only github single-MCP. Reads contexts/ticket-input.md as fallback. Saves ~15-40K per story.

MCP-failure recovery gates

If an MCP probe fails mid-run, Orchestrator opens an inline gate: retry / inline / file / skip / cancel. No re-trigger needed; you handle the fallback in the same conversation.

Explorer — key capabilities

Map Sync (every story)

Every Incremental Mode run syncs the codebase map before exploration. Uses git log --after=last_synced_at on both develop (merged PRs) and current branch (stacked work) to find all changed files. Stale entries updated in-place, new files from prior stories appended. Map is always current — no manual triggers needed.

Epic codebase map

Built once by the first story (Full Mode). Contains shared components, services, REST endpoints, conventions, and reference implementations. Metadata header tracks last_synced_at, stories_completed, and a story_log audit trail. Ship agent increments the counter after each push.

Stale + new file detection

comm -12 finds files in the map that changed (stale → update in-place). comm -23 finds files created by prior stories not in the map (new → scan and append). New files in common/shared/service/directive dirs are always scanned — even if not in the current LLD.

Reuse detection

When prior stories created files that this story's LLD references, Explorer flags them as reuse candidates: task status changes to 🟡 PARTIALLY DONE or 🔧 NEEDS MODIFICATION instead of 🆕 NEW. Prevents duplicate implementations across an epic.

Smart file reading

<200 lines: read fully. 200–500: structure + target methods. 500+: method signatures only. Scales reading depth with context pressure.

Task annotation summary

Compact table with file paths, insertion points, reuse flags (🆕 REUSE from {TICKET}), and gotchas — the surgeon's working blueprint.

Surgeon — key capabilities

Dependency-ordered per-task loop

Implements tasks in strict dependency order from $LLD_FILE PART 2. Each T* task is completed before its dependent T-TC* test task begins. Layer-aware: loads only the relevant pack skill from skills.layer_map per task.

Per-task build SKIPPED

Big change: per-task ant build was removed — it was the single largest source of context bloat. Per-task = lint + unit tests only. Full build runs ONCE at final_build_check (Step 4). ~99% reduction in build-output tokens.

Build runner wrapper (mandatory)

Every shell invocation goes through builds.runner.template_with_report. Tool result = exit=N (~5 tokens). Raw stdout/stderr → builds.runner.log_path. Verdict + tail_30 → $SURGEON_BUILD_REPORT. Read on demand only.

Build-failure gate

5-attempt auto-fix loop. On final failure: retry / skip / cancel. skip records to manifest; Review's full clean build is the backstop. Forbidden commands blocklist (*deploy*, db drops, force pushes) is checked before every eval.

Subagent extension points

surgeon_pre_task and surgeon_post_task hooks fire if a pack supplies them — useful for project-specific guard checks. Empty by default = zero cost.

Standalone mode

Apply: <spec> in <files> for one-off fixes (≤5 files / ≤150 lines). Implement: + bullet ACs (≤5 ACs). Output to contexts/standalone/. Over cap → halts with "use pipeline instead".

Git-write-only via Ship

Surgeon writes code but NEVER runs git add / commit / push. All git ops are owned exclusively by Ship — clean separation of concerns.

UI edge-case checklist

For every frontend task: null data, empty lists, slow networks, failed requests. Mandatory — these are the #1 source of "works in testing, breaks for customers" bugs. Plus ARIA + i18n key resolution.

AC-E2E-Check — key capabilities OPTIONAL · Step 3.5

Browser AC verification

Drives a real browser through every AC. Captures screenshots, validates DOM state, confirms behavior matches the LLD. Sits between Surgeon and Review.

Default: trust the dev server

run_build defaults to false — assumes dev server is already up (Tomcat / npm run dev / flask run). Skips a redundant rebuild Surgeon already verified. Set run_build: true only for remote-env flows.

Gap analysis emits new tasks

If browser behavior diverges from the AC, AC-E2E-Check appends new tasks to the LLD. Re-run Surgeon; loop until clean. No silent skipping of misbehaving ACs.

Optional E2E spec generation

Generates Cypress / Playwright specs per AC into demo.e2e.<framework>.spec_dir. Ready for CI runs.

Review — key capabilities

Full + slim modes. Full is mandatory before Ship. Slim trusts Surgeon's per-task work for fast integration check (--slim).

Build report freshness reuse

Big change: if $SURGEON_BUILD_REPORT.verdict == PASS AND started_at > manifest_mtime, Review skips its own builds.review_gate entirely. Saves 2-5 min + a full build's worth of tokens.

Build runner wrapper (mandatory)

If Review does run a build, every invocation is wrapped via builds.runner.template_with_report. Fix loop capped at 3 iterations (down from 10). Each re-run overwrites the report file.

Per-layer test suites

Runs builds.review_test_suite.* per layer (e.g. ant jstests, ant jtest, ng test). Each layer writes its own report file (...-tests-js.md, ...-tests-java.md) so a JS failure doesn't overwrite a Java pass.

AC compliance check

Walks the Enriched AC Registry. For each AC: was a task implemented? Does the diff cover it? Are tests in place? Verdict per AC: PASS / WEAK / MISSING.

Pattern + visual fidelity

If a reference ticket was declared, Review compares the diff to the reference's PR (via GitHub MCP) for pattern adherence. If design images present, Review compares rendered screenshots to the design.

Epic-context append

After every shipped story, Review appends a compact entry to $EPIC_CONTEXT — CREATED / MODIFIED / CONFIG files + decisions made. Next story's Orchestrator reads this so the epic accumulates institutional knowledge.

Subagent extension

review_post_check hook fires after AC compliance — useful for pack-specific compliance scans. Empty by default.

Standalone modes

3 sub-modes: Review changes (diff only), Review <TICKET> (AC coverage), Review against: + bullets (ad-hoc ACs).

Ship — key capabilities

Build verdict pre-flight

Reads all $*_BUILD_REPORT files. If any verdict: FAIL, halts immediately — Ship should NEVER produce a PR with a failed build. Reads only YAML front-matter (status / verdict / duration_s); never tail_30 in PR body.

Commit strategy choice

Asks developer: single commit, per-task commits, or custom grouping. Uses manifest to generate descriptive commit messages with ticket IDs. Build report files are committed alongside the diff.

Double-gated push

Gate 1: git status + diff summary + pre-push checklist. Gate 2: developer types "Confirmed" before git push executes. No accidental pushes.

PR with build verdicts table

PR body includes: task list, AC compliance, blast radius, rollback instructions, and a build verdicts table from the report files. Reviewers can open the report files in the branch for raw error tails.

JIRA transitions

Transitions the ticket per jira.transitions: e.g. In Progress → In Review on PR open. Configurable per project.

Codebase map metadata

After successful push: increments stories_completed, appends STORY_SHIPPED to story_log. Next Explorer run uses last_synced_at to find merged-PR file changes.

No standalone mode (by design)

Ship requires Review's verdict and a manifest. Use @orchestrator.md Work on <TICKET> for full pipeline OR @surgeon.md Apply: + manual git commit for one-offs.

Subagents

Two kernel subagents — when delegation actually saves tokens

Subagents are delegated workers invoked at extension points. They run in their own conversation, take inputs, and return a small structured result. The kernel ships two: Amender (fires at Orchestrator's Phase C gate) and Image-Analysis (fires inside Orchestrator's enrichment phase). Both fit the subagent pattern: heavy intermediate data and compact returns.

Amender — targeted LLD edits

Fires on Amend: <text>

Triggered at Orchestrator's gate_for_approval (C) gate. Cannot fire after Explorer has run (any downstream artifact = refuse + tell user to cancel and re-run from Orchestrator).

Section-level diff plan

Phase 2 builds a Section Impact Map — every ## heading across the 3 LLD files marked ADD / MODIFY / DELETE / UNCHANGED. User approves the plan before any file is edited.

7 amendment classifications

Functional addition · AC addition · AC modification · Design change · Constraint addition · Scope reduction · Clarification only. If amendment fits multiple, splits into sequential amendments with their own gates.

v15 marker preservation

Phase 1.5 protects machine-readable markers (Button Intents table, Promotion Annotations, Confidence labels) byte-for-byte. Corrupting a marker silently breaks Explorer / Surgeon wiring.

Routes edits to correct file

Requirement Summary + ACs → $CONTEXTS_FILE. PART 1/2 → $LLD_FILE. PART 3/4 → $TESTPLAN_FILE. The Section Impact Map tags every change with its target file.

~6× cheaper than re-running Orchestrator

Re-running Orchestrator means re-fetching JIRA, re-fetching Confluence, re-fetching Figma, re-rendering everything. Amender reads the 3 files fresh, edits only what changes, bumps version + amendment log.

Image-Analysis — keeps raw image bytes out of Orchestrator

Spawned during enrichment (A0.6)

Orchestrator's resolve_enrichments phase fires this when at least one image source is present (drag-drop, JIRA attachment, Figma fetch).

Loads minimal config

Reads ONLY pipeline.yaml core + analyzer.yaml (for component matching against shared_paths). No skills, no ticket schema, no LLD generator — saves ~25K of subagent overhead.

Returns compact visual_spec

Raw image bytes can be 15-25K tokens each. Subagent extracts component structure, states, spacing, copy. Returns a ~3K structured spec. Raw bytes never enter Orchestrator's context.

Used by A.5 + B.3

build_requirement_summary (A.5) writes a Visual Specification section. synthesize_lld (B.3) uses the spec to bias task decomposition (e.g. "shared component X matches the design — REUSE not CREATE").

Guardrails

Rules, skills, and what they prevent

Three tiers of injected behavior. Tier 1 always-on rules from agent-flow.mdc. Tier 2 on-demand skills (LLD generator, layer standards, AC templates). Tier 3 pack-supplied subagents at extension points.

Tier 1 — Shared rules (agent-flow.mdc — always active)

Build safety + forbidden commands

builds.forbidden denylist checked before every eval: *deploy*, db drop/truncate, git push --force*. Universal across all agents.

Error escalation

Try fix 3-5 times → present options → NEVER silently skip. User always decides. Surgeon caps at 5; Review at 3.

No hallucinated paths

Every file path verified with ls before referencing. Prevents "file not found" during implementation.

Branch + git safety

Feature branch only (runtime.branching.prefix_story / prefix_bug). Only Ship runs git add/commit/push. Surgeon writes but never commits.

Never silently skip

Missing Figma, HLD, ACs, API specs → STOP and ask. User must explicitly say "skip" or provide input.

Token awareness + per-agent budgets

Running low → STOP, save progress to file, provide resume instructions. Every agent records its token usage as a comment in its output file; Review compiles a pipeline-wide table.

Path resolution (Procedure B)

Every non-Orchestrator agent globs contexts/**/{TICKET}.md at pre-flight. Halts on no match or ambiguous match (multiple files in different folders). Both nested_by_epic: true/false layouts coexist.

Build report contract

Every build via builds.runner writes a structured report file (front-matter + tail_30). Review reuses Surgeon's report if fresh. Ship attaches verdicts to the PR. No agent ever carries raw build output past one turn.

Tier 3 — Subagents (pack-supplied at extension points)

The Amender is a subagent because section-classification + diff-planning generates lots of intermediate tokens Orchestrator never needs. See the "Subagents" section above for extension-point details.

Context lifecycle — file-based handoffs + overflow recovery
1. Smart reading

<200 lines: read fully. 200-500: structure + target methods. 500+: method only. Scales with token pressure.

2. File handoffs (the big one)

Each agent saves output to file and exits. Next agent reads the file, not chat history. New conversation works. No long-running session required.

3. Compact Task Annotation Summary

Surgeon reads a 20-line table per task. Full exploration report only when the table lacks detail.

4. File-by-file review

Review diffs one task at a time. Releases each from memory before loading the next.

5. Build runner wrapper

Tool result is exit=N (~5 tokens). Raw output → log file. Verdict + tail_30 → report file. ~99% reduction vs raw eval.

6. Epic context reuse

1st story builds epic-context.md. Stories 2+ skip Confluence HLD fetch — read the local file. ~10-15K saved per story.

7. Codebase map sync

Explorer syncs the per-epic map every run via last_synced_at. Stale entries updated in-place; new files appended. No re-scanning the world.

8. Three-file LLD split

Surgeon never reads design discussion. Review rarely reads the AC Registry. Each agent loads only what it needs (~10-15K saved).

9. Per-task build SKIPPED

The single largest source of context bloat eliminated. 10-task story used to run 10 full builds (~300K tokens of output). Now: 1 final build via the runner = ~5 tokens.

Key insight: Start any agent in a NEW conversation and it works — it reads saved files, not chat history. If surgeon overflows at task 8, resume from task 8 in a fresh conversation.
Build runner contract

Build output is treated as a side effect, not conversation content

Review's freshness check (the third mechanism)

IF $SURGEON_BUILD_REPORT exists:
    parse front-matter → .verdict, .started_at, .command
    manifest_mtime = max(mtime of files in $MANIFEST_FILE)
    IF .verdict == PASS AND .started_at > manifest_mtime
                       AND .command == $(yaml_get builds.review_gate):
        → reuse Surgeon's verdict — skip review_gate entirely
        → save 2-5 minutes + a full build's worth of tokens
    ELSE:
        → run review_gate fresh, write $REVIEW_BUILD_REPORT

MCP failure recovery (no re-trigger needed)

Atlassian fails mid-run

Inline gate: retry / inline / file / skip / cancel. inline + paste Context: block → parsed as if from JIRA. file + fill ticket-input.md → continue.

Silent degradation

If the failure is immaterial (Figma down + ticket has no Figma URLs / Atlassian down + ticket-input.md is filled / GitHub down + no reference declared), Orchestrator notes it in the Active Context block and continues without a gate.

Subsequent stories save more

Stories 2+ in an epic skip Confluence HLD fetch — they read the local epic-context.md. --skip atlassian on a 5th story only loses the sibling drift check — usually free.

Active Context block printed at every Orchestrator pre-flight shows: ticket + mode, MCP status (✓ / ✗ / skipped), input sources used, recoveries applied. You always see what actually drove the run.
