The big idea

One principle: state lives in files, not chat

Everything else follows from this. Each agent runs in its own short-lived conversation, reads its inputs from disk, writes its outputs to disk, and exits. The next agent reads only the files — never the previous chat. That is what makes gates, hand-offs, and day-2 resume work.

Three consequences to keep in mind while reading:
  • You are the scheduler. Typing the next agent IS the gate. No agent runs another agent.
  • Context is a budget. Every file read costs tokens, so agents load only the slice they need — this is why the LLD is split into 3 files and skills load on demand.
  • Rules always apply; skills apply on demand; subagents are invoked. That's the three-tier system below.

The 2 subagents

Delegated workers & the invocation contract

A subagent runs in its own context window, takes one YAML input block, and returns one compact YAML result. Its value is context isolation — heavy data (raw JSON, image bytes, grep output) stays in the subagent's transcript, and only the summary crosses back to the parent.

The contract (5 conventions):
  • Single YAML output — one fenced block starting with status: ok | error | partial + schema_version. No prose.
  • Input as one YAML block in the invocation prompt — the subagent reads only that, no free-form instructions.
  • Deterministic cache at contexts/<epic>/_cache/<subagent>-<key>.yaml — the key includes an external version id (e.g. PR head SHA) so stale caches invalidate naturally.
  • Never gates the user — only the parent owns interaction. On error the parent surfaces the reason at its next gate and takes a degraded path.
  • Emits its own tool-usage log to contexts/<epic>/_subagents/.

Tier 1 · Rules

Rules — always on, every run

A rule is a .mdc file with alwaysApply: true in its frontmatter. The host tool (Cursor / Claude Code) injects it into every agent run's system context automatically — the agent doesn't choose to load it. That is the entire Tier-1 mechanism.

The three kernel rule files

engineering-principles.mdcTech-agnostic SOLID / KISS / DRY / YAGNI / POLA + cross-cutting concerns. Two modes (greenfield vs legacy). Surgeon self-checks per task.
{pack}-project-scope.mdcPack-specific repo boundary + build/forbidden targets (data lives in builds.* of the pack YAML)

engineering-principles — greenfield vs legacy modeapplies at Surgeon task time

Loads every run but applies to every task that writes code. The mode is chosen per task from the LLD PART 2 status field — no separate detection:

  • 🆕 NEW / IMPLEMENT → Greenfield — all 25 principles apply fully.
  • 🟡 EXTEND / 🔧 MODIFY → Legacy — apply only to added/changed lines; match surrounding style; do NOT refactor. Principle #0 "Match the neighborhood" overrides everything.
  • ✅ ALREADY DONE → no-op.
Anti-principles (explicit rejections): the Boy Scout Rule is REJECTED — no opportunistic refactor. Discomfort about legacy code goes into the manifest's Legacy observations section, never the diff. Self-check runs at post_verification step 3; each task's manifest carries a line T{N}: principles · Mode: {greenfield|legacy} · exceptions: {N}.

Conflict order (most-specific wins): task's LLD contract → local file conventions → pack rules → engineering-principles → the agent's own preferences.

Tier 3 note: pack subagents wire at four extension points — orchestrator_amend_request (kernel ships Amender), surgeon_pre_task, surgeon_post_task, review_post_check. Unlike rules (always injected) and skills (catted in as reference), subagents are invoked — the parent hands over control and acts on the structured return. The your-project pack ships none, inheriting the kernel defaults.
Tier 2 · Skills

Skills — loaded only when triggered

Skills are .md reference files catted into an agent's context on demand. This is the whole reason a pack can ship seven layer-standard skills without bloating every run. They trigger two ways: per task (Surgeon) and per run (agent slots).

Per-task loading — Surgeon's layer_map (2 strategies, union)Surgeon Step 0a

For EACH task, Surgeon resolves skills two ways and takes the union:

  • Strategy A — path_glob: match the task's Files against each layer_map entry's glob. A task touching frontend/src/app/user.component.ts matches Frontend/Angular18's glob → loads angular18-standards.md.
  • Strategy B — Layer string: normalize task.Layer and match against each entry's key + aliases. task.Layer = "React" matches Frontend/React aliases.

The skill body is catted in only when a task triggers it, and the previous task's skill is released before the next loads. A layer_map entry looks like:

"Frontend/Angular18":
  skills: [your-project-angular18-standards.md]   # catted on match
  path_glob: "frontend/src/**/*.{ts,html}"        # Strategy A
  build: ui_dev                                    # → builds.commands.ui_dev
  desc: "Angular 18 — NgModule, RxJS, reactive forms"
  aliases: ["Angular18", "Angular 18", "ng18"]     # Strategy B

Shipped keys: Frontend/Angular18, /Angular19, /React, /Vue, JavaScript, TypeScript, Backend/Java, Test (no path_glob — tests live anywhere, so Strategy B only). extra_triggers fire additively on top (e.g. add a11y or security standards when a natural-language condition matches).

Per-run loading — agent slots (once at startup)no triggers

Some skills load once per invocation, unconditionally, because they apply to the whole run:

  • orchestrator.lld_generator — the LLD generator (Story mode); also ticket_schema_story, ac_templates_intent_aware
  • explorer.bug_router / bug_frontend / bug_backend — bug-localization sub-skills (Bug mode)

In your-project these slots are unset, so Orchestrator/Explorer fall back to kernel defaults (ticket-schema-template.md, ac-templates-intent-aware-generic.md).

The difference that matters: per-run slots load once at startup regardless of the work; layer_map skills load per task, only on a match — which is the token-saving lever.

Pipeline config

The config — the trigger map every agent reads

The config is the pipeline's wiring diagram: which skill loads for which layer, what builds run, which MCPs back which roles, how tickets route. The kernel is pack-agnostic — the agent prompts never hardcode a project; they read all project specifics from the config. That's why the same prompts work for any pack.

One seed → five split files. A pack ships one monolithic seed at packs/<pack>/pipeline.<pack>.yaml. The installer splits it at install time into five files under contexts/config/ so each agent loads only the slice it needs (~10K tokens saved per agent). The seed itself is not copied into the project — agents read the splits.

Pack resolution — how {PACK} is discoveredonce, at pre-flight

Kernel prompts reference config as pipeline.{PACK}.<role>.yaml. At pre-flight each agent resolves {PACK} once and reuses it:

glob  contexts/config/pipeline.*.yaml
keep  the single-dot "core" stem   # pipeline.<pack>.yaml, not .skills/.builds/…
read  meta.pack  from that core file
→ substitute that value for {PACK} everywhere

Zero core YAMLs → halt Pack not installed. Multiple → halt Ambiguous install. meta.pack ≠ filename stem → halt. This is the mechanism that lets one kernel serve your-project or any custom pack with no prompt changes.

codebase-map.md — the Explorer↔Ship contractsynced every story

An epic-level knowledge base shared across all stories. Explorer owns content; Ship owns metadata (stories_completed, story_log). On story 2+, Explorer syncs it every run (Phase 1.5):

read last_synced_at

git log {base}..HEAD                     # current branch
comm -12 → stale files  (update in-place)
comm -23 → new files    (scan + append)
bump last_synced_at

Two mutations only — update-in-place and append. Entries are never removed. last_synced_at is the single source of truth for new-vs-known.

A compact companion to the codebase map that replaces expensive sibling-LLD lookups. Build reports — keeping build output out of contextstructured YAML, tail_30 only

Every build through the runner writes a structured YAML-frontmatter report alongside the raw log:

agent: surgeon
phase: final_build_check
command: 'ant clean build'
status: 0

duration_s: 47
log_path: ...          # full log stays on disk
tail_30: |             # last 30 lines only

Reading discipline: on PASS read only the frontmatter (verdict/duration) — not tail_30; on FAIL read the full report incl. tail_30, escalating to log_path only if needed. This is the mechanism by which no agent carries raw build output in its transcript. Ship commits the reports to git so the PR's build-verdict table is auditable.

Day-2 resume & the nested layoutnew chat = fresh context

To resume in a new conversation, an agent: (1) re-reads its own prompt automatically, (2) re-reads saved artifacts (LLD, exploration, manifest), (3) skips completed tasks (checks the Change Manifest / task reports), (4) continues from the pending task. Trigger: Resume {agent} for {TICKET} from task T{N}.

Layout (runtime.contexts_layout.nested_by_epic: true): artifacts nest under contexts/<epic>/ with a per-epic codebase-map.md. Downstream agents glob-discover the context file — glob "contexts/**/{TICKET}.md" (matching {T}.md exactly, so the -lld/-testplan companions don't shadow it). 0 matches → halt; 2+ → halt (ambiguous). Flat mode and nested mode coexist safely because discovery is glob-based, not path-hardcoded.

Harness & loop engineering

The machinery that keeps runs safe and cheap

These are the cross-cutting mechanics in agent-flow.mdc that every agent inherits — how the pipeline simulates a context window it can't query, resumes long loops, and keeps prompt caches warm across hand-offs.

Context Pressure Detection — 4 zonesthe LLM can't query its own window, so it counts

Each agent keeps a running token counter: seed = ceil(chars(system + prompt + skills + rules) / 4), then += ceil(chars / 4) on every Read, Bash output, Grep result, and assistant turn. At every gate it computes ratio = counter / estimated_window (200K) and resolves a zone:

GREEN <60% — gate shown verbatim, no annotation.
YELLOW ≥60% — banner prepended, recommends a fresh-chat handoff; continuing allowed.
ORANGE ≥80% — replaces the gate; you must pick Resume in fresh chat (deeplink) / Continue anyway / Pause.
RED ≥90% — replaces the gate AND halts immediately, refusing input until you type verbatim Override pressure halt — I accept the risk. State is flushed to disk first.

The pre-flight Active-context block always shows Context pressure: ▒▒▒▒▒░░░░░ N% · {zone}. Every gate is a checkpoint; some agents also check mid-step (e.g. Surgeon between reuse Reads and implement).

The per-task loop & token-aware resumesave manifest, resume in fresh chat

On low context mid-loop, Surgeon STOPs, saves completed work to the Change Manifest, and prints resume instructions (Resume surgeon for {T} from task T{N}) listing done / pending / files-to-read. Bundle mode formalizes this in _bundle-state.yaml with a resume cursor: last_task = highest complete index; next = last_task+1; the file is written atomically (.tmp then rename) at every checkpoint. A stage re-enters in_progress from failed only after you pick Resume from T<N>.

Deeplink / fresh-chat handoffwhy hand-offs start a new tab

Every inter-agent gate offers a Cursor deeplink: cursor://…/prompt?text={URL-encoded command}. Clicking opens a new chat tab with the trigger pre-filled — so the prior agent's tool outputs don't bloat the next agent's context, and prompt caching on stable files (pipeline YAML, project-map, skills) stays warm. This is the direct implementation of "handoff via files, not chat."

Deeplinks are ONLY for inter-agent handoffs; in-chat options (Amend:, Go, retry) get none. Claude Code has no URL scheme, so the deeplink renders as plain text you copy into a new conversation. Mandatory: the last thing in every agent response is a 👉 Next action block — a response without it is incomplete.

Tool-usage ledgerwhat each run actually cost

Every agent appends a block to $TOOL_USAGE_FILE before its final gate, regardless of verdict. It captures MCP calls, git ops, bash invocations, file reads/writes (bytes ≈ tokens×4), build invocations (exact durations from the report), and an estimated cost with per-model rates. Subagents write their own logs to contexts/<epic>/_subagents/. Roll up across stories with node contexts/tools/aggregate-tool-usage.mjs. Counts are exact; token/cost estimates are ±~30% (the agent doesn't see API billing).

Invocation modes, pack resolution & MCP roleshow an agent bootstraps

Invocation mode — the first pre-flight step detect_invocation_mode (0) parses the trigger: pipeline (full chain) vs standalone (ad-hoc, reduced flow, output under contexts/standalone/). Ship rejects standalone as a safety rail.

Pack resolution — {PACK} is resolved once at pre-flight: glob contexts/config/pipeline.*.yaml, keep the single-dot core stem, read meta.pack. Zero or multiple cores → halt. This is why the same kernel agent prompt works for any pack.

MCP roles — agents never hardcode MCP names; they consult mcp_roles (story_source, design_source, vcs, docs_source). Resolution ladder per run: config opt-out → flag overrides (--offline/--skip) → walk the fallback list → probe host → else local fallback (ticket-input.md) or halt.

Post-execution verificationfail-loud harness check

After any trigger, the routing layer silently checks that expected outputs exist (per a per-trigger table — e.g. Run the surgeon → manifest exists + git status shows uncommitted changes in the named files; any run → a new block in the tool-usage ledger). If something's missing it emits a structured ⚠ Agent execution verification FAILED diagnostic with likely causes and fix options (including the explicit @<agent>.md form). It's passive — never auto-retries. Force it anytime with Verify last agent run.
