Business problem · solution · use cases

Ticket-to-PR is slow, inconsistent, and costly — we fixed it with a pipeline of agents

The work between "here's a JIRA ticket" and "here's a reviewed PR" is repetitive and error-prone, and a single AI prompt can't do it reliably. We solved it with a team of specialized AI agents on an engineered harness — human-gated, file-driven, stack-agnostic. The payoff: an 8-point story that used to take days now ships in about an hour. Here's the business problem, how it's solved, and the three use cases that matter most.

Business problem

Why a single AI prompt can't ship a story

AI can write code fast — but it can't reliably ship a story on its own. Point one big prompt at a repo and it loses context, hallucinates file paths, duplicates code, and makes risky commits with no audit trail or cost control. Speed without governance isn't shippable.

🧵
Loses the thread

One prompt holding the ticket, codebase search, implementation, tests, and git in a single context drifts off track and overflows its window mid-task — then can't resume.

🔁
Hallucinates & duplicates

It invents file paths that don't exist and rebuilds components a sibling story already shipped, because it has no reliable, current view of the codebase.

🎚️
Unverified quality

Standards, edge cases, and test coverage vary run to run — with no AC-by-AC compliance check and no blast-radius awareness on shared code.

⚠️
Risky & opaque

Destructive commands, half-finished commits, no record of why it did what it did, and a token bill you can't forecast.

The core tension: the business needs the speed of AI with the governance of a real engineering process. A single mega-prompt holds the whole ticket — parsing, search, implementation, tests, review, git — in one context. It loses track, duplicates work, and gives you no control points.
How we solved it

A team of agents, not one big prompt

Story2PR splits the work into narrow agents on an engineered harness — file-based state, approval gates, safety rules, and subagents for isolation — giving AI speed with the governance of a real engineering process. Each agent runs in its own short-lived conversation with defined inputs and outputs; you're the scheduler, and typing the next agent is the approval gate. Each one closes a specific failure mode above.

~1 hr
an 8-point story
The headline: an 8-story-point ticket ships in about an hour. Work that traditionally spans days — reading the ticket, hunting the codebase, coding, testing, reviewing, raising the PR — compresses into one gated session. The agents do the repetitive middle; you just approve each turn. Across a sprint that's the difference between clearing a few stories and clearing the backlog.

Each failure mode from the problem section maps to a specific agent (and, where it helps, a subagent) that closes it:

Loses the threadOne context drifts and overflows mid-task
→
Narrow agents, state in files: each of the five agents runs in its own short context and hands off through files — there's no single thread to lose, and context-pressure zones force a clean handoff before overflow. The image-analysis subagent keeps heavy design bytes out of the Orchestrator.
Hallucinates & duplicatesInvents paths, rebuilds existing code
→
Explorer greps the shared_paths registry in the codebase map and downgrades a "create" task to "reuse / modify" before code is written; the no-hallucinated-paths rule ls-verifies every path.
Unverified qualityStandards + edge cases vary run to run
→
Surgeon → Review: Surgeon loads the right layer standards per task + runs per-task lint/tests + an edge-case checklist; Review runs the full build, AC-by-AC compliance, and blast-radius on shared code → a ship-ready YES/NO verdict.
Risky & opaqueUnsafe commits, no trail, no cost control
→
Ship + the harness: only Ship touches git (double-gated); a forbidden-command denylist blocks destructive ops; every decision, build verdict, and cost is written to a per-story ledger. The amender subagent edits the plan ~6× cheaper than a re-run.
The two subagents keep runs cheap and reliable by isolating heavy work: image-analysis compresses a 15–25K-token design image into a ~3K spec that never bloats the Orchestrator; amender makes targeted plan edits instead of re-fetching JIRA + Confluence + Figma. Full agent / subagent / harness detail is in How It Works.html; the step-by-step run in How To Use.html.

What makes it reliable — the harness

Specialized agents are the idea; the harness is the engineering that makes them dependable and affordable.

🗂️ State in files

Each agent reads only the slice it needs and writes results to disk. The next agent reads the file, not the chat — so runs are auditable, resumable, and cheap.

📉 Context-pressure limits

Each agent tracks its own token use and hands off to a fresh chat before it overflows — no silent degradation mid-task.

🛡️ Always-on guardrails

Forbidden-command denylist, git-ownership, branch safety, and "never silently skip" are injected into every run — safety doesn't depend on memory.

Why it's affordable: the file-state + caching design keeps real cost around $3–6 per agent (≈$15–30 for a full cold story) with a per-story ledger — instead of the multiples an always-re-reading mega-prompt would burn.
Use cases

The three that matter most

The same machinery covers many scenarios; these three carry the business value — everyday delivery, defect resolution, and delivering related work at scale.

1New feature story, end-to-endeveryday delivery

How we addressed it: the six-agent pipeline takes a well-defined story from ticket to reviewed PR. The Orchestrator writes a 3-file plan, the Explorer finds reuse and insertion points, the Surgeon implements task-by-task with per-task tests, the Review agent runs the full build + AC compliance + blast radius, and Ship opens the PR — a human gate between each.

Example
JIRSTORY-1234 — "Add an entitlement filter to the certification list page." A UI story under an existing epic, with a Figma design attached. Explorer finds the existing sp-dropdown to reuse; Surgeon wires it + session-storage persistence; Review confirms all 3 ACs pass.
How to run
@orchestrator.md Work on JIRSTORY-1234   # + attach design → Phase C gate: reply "Go"
@explorer.md Run the explorer          # review annotations
@surgeon.md Run the surgeon            # per-task loop + final build
@review.md Run the review             # reply "Fix all P1" if needed
@ship.md Ship it                       # "Single commit" → "Confirmed"
Run it offline / privately
Same six steps, no external calls — add --offline and provide the ticket via contexts/ticket-input.md + attached images: @orchestrator.md Work on JIRSTORY-1234 --offline. Use --skip atlassian to skip only JIRA. Saves ~15–40K tokens and keeps ticket content off external services.
Value: consistent quality with no duplicated code, and a PR that already carries its test plan, blast radius, and AC compliance — so review is fast.
2Bug fix — root cause, not guessworkdefect resolution

How we addressed it: the Orchestrator detects a Bug issue-type and switches the plan shape — the test-plan section becomes "Root Cause Hypotheses," and the Explorer routes to bug-localization instead of feature exploration. The fix is scoped to the actual cause, then verified like any story. Same triggers as a feature — the mode is auto-detected.

Example
JIRSTORY-2101 — "Date-picker selection doesn't persist after reload." Orchestrator lists root-cause hypotheses (session-storage key mismatch vs init order); Explorer localizes to the controller's init; Surgeon fixes the load order; Review confirms the regression is gone.
How to run
@orchestrator.md Work on JIRSTORY-2101   # Bug type auto-detected → Go
@explorer.md Run the explorer          # bug-localization pass
@surgeon.md Run the surgeon
@review.md Run the review
@ship.md Ship it
Value: structured root-cause reasoning and a targeted, tested fix — fewer "patched the symptom, missed the cause" regressions.
3Multi-story epic — bundle modescale & cost

How we addressed it: dedicated bundle-* agents consolidate 2–10 related stories into ONE plan, ONE branch, ONE PR. Overlapping code is de-duplicated at design time, tasks are ordered by layer and dependency so shared work is built once, and the Surgeon + Review checkpoint every few tasks to keep context healthy. One PR closes every shipped ticket, each with its own JIRA transition.

Example
JIRSTORY-1234, -1235, -1236 — three stories in the same epic that all touch the notifications panel. Bundled, the shared panel component is built once and reused across all three, instead of three separate PRs each re-touching it.
How to run
@bundle-orchestrator.md Work on epic stories JIRSTORY-1234, JIRSTORY-1235, JIRSTORY-1236
# or by status:  @bundle-orchestrator.md Work on epic JIRSTORY-EPIC-42 with status="Ready for Dev"
@bundle-explorer.md Run the bundle explorer
@bundle-surgeon.md Run the bundle surgeon
@bundle-review.md Run the bundle review
@bundle-ship.md Ship the bundle
Value: ~30–40% faster wall-clock and one PR to review instead of N — roughly 50% cheaper than shipping the same stories cold and separately.

Also runnable — two modes on top of the above

These aren't separate work types — they're ways to run the same agents, so they layer onto any of the three use cases above.

🔌
Offline / sensitive

Any pipeline run with --offline or --skip <mcp> — feed the ticket via contexts/ticket-input.md + local images. No network calls, keeps content off external services (regulated or air-gapped work), and saves ~15–40K tokens.
@orchestrator.md Work on JIRSTORY-1234 --offline

🧩
Standalone — no ticket

Single-agent, ad-hoc runs for quick research or a small targeted fix; output lands in contexts/standalone/. Size caps apply (Surgeon ≤5 files / ≤150 lines). No standalone for Ship — it requires a Review.
@explorer.md Research: <question>
@surgeon.md Apply: <fix> in <files>
@review.md Review changes
