Getting started

How you kick it off

Start the orchestrator on your ticket. It plans; you approve; each agent hands off to the next through a file on disk.

@orchestrator.md Work on JIRSTORY-1234

[ Orchestrator → Explorer → Surgeon → (AC-E2E-Check, optional) → Review → Ship ]
      gate          gate       gate           gate                gate     gate
Both forms work. @orchestrator.md Work on JIRSTORY-1234 and plain Work on JIRSTORY-1234 are equivalent — the plain trigger routes to the orchestrator via the auto-start rule in agent-flow.mdc. The @-prefix is recommended because it forces the agent file to load explicitly (more reliable in Cursor). Claude Code handles the plain form reliably too.

Step by step

"Work on JIRSTORY-1234"

A medium UI story under epic JIRSTORY-1200. Each step shows what you type, the gate, the rules / skills in play, and the subagents that fire.

Orchestrator 3-file LLD + branch

@orchestrator.md Work on JIRSTORY-1234  (attach a design image if you have one)
Reads the ticket, walks the parent to epic JIRSTORY-1200, inherits epic-context.md, resolves the design, and writes the three companion files. The epic + reference enrichment is fetched inline; when a design is present the image-analysis subagent turns the Figma frame into a compact visual_spec so raw image bytes never enter its context. Then it stops at the Phase C gate.
⏸ Phase C · Amend / Go / Cancel image-analysis (if image) amender (on Amend:) skill: lld_generator rule: never-silently-skip
You reply: Go → branch created  (or Amend: <change> → spawns amender, ~6× cheaper than re-running)

📄 JIRSTORY-1234.md · -lld.md · -testplan.md · branch

Explorer sync + explore

@explorer.md Run the explorer
Syncs the codebase map with sibling changes (git log), then explores each task — finding the exact insertion point, deciding NEW / MODIFY / REUSE, and writing a compact result the Surgeon reads verbatim. Reuse gets caught here: a "create directive" task is downgraded to MODIFY if a sibling already shipped it.
⏸ review annotations rule: no-hallucinated-paths (ls-verify) rule: smart-read by file size
Usually: @surgeon.md Run the surgeon

📄 JIRSTORY-1234-exploration.md + synced codebase-map.md

Surgeon per-task loop

@surgeon.md Run the surgeon
Implements tasks in dependency order (DB → backend → REST → frontend). Per task = load the layer skill, change code, lint + unit test (auto-retries a lint fail up to 5×). The full build runs once at the end and writes a build report. Surgeon writes code but never commits.
⏸ after final build skill: layer_map (per task) rule: builds.forbidden denylist rule: git ownership (no commit)
Optional: @ac-e2e-check.md Demo JIRSTORY-1234 → then @review.md Run the review

📄 code changes + JIRSTORY-1234-manifest.md + build report

Review verify everything

@review.md Run the review  (add --slim to trust Surgeon's per-task work)
Reuses the Surgeon build if it's fresh. Reviews each task's diff against the LLD, computes blast radius for downstream impact, checks pattern + visual fidelity, and verifies every AC — all inline. Appends this ticket's file list to epic-context.md for the next story. Emits ship-ready YES/NO.
⏸ ship-ready YES/NO rule: build-report reuse (freshness) rule: blast-radius on shared code
You reply: Fix all P1 → then @ship.md Ship it

📄 JIRSTORY-1234-review.md + epic-context.md (appended)

Ship commit + PR + JIRA

@ship.md Ship it
Pre-flight reads every build verdict — any FAIL halts (no PR on a broken build). Then it asks commit strategy, shows the pre-push checklist, waits for "Confirmed", pushes, opens the PR (task list + test plan + blast radius + rollback + AC summary), and transitions JIRA. The only agent allowed to touch git.
⏸ commit strategy ⏸ "Confirmed" before push rule: git ownership rule: build-verdict pre-flight halt
You reply: Single commit → Confirmed → PR created → JIRA transitioned ✅
Stuck at a gate? Every agent's halt message tells you the exact command to run next. State lives in files, so you can stop after any gate and resume the next day with the same trigger.
Subagents

The 2 subagents — where each fires

Subagents are delegated workers. They take a big input, return a small structured result, and keep heavy data (image bytes, raw JSON) out of the parent agent's context. The kernel ships two.

SubagentFires inDoes
image-analysisOrchestrator (A0.6)Figma frames / screenshots → ~3K visual_spec. Raw image bytes stay out of context.
amenderOrchestrator Phase C gateSurgical LLD edits on Amend:. Refuses once Explorer has run. ~6× cheaper than re-running Orchestrator.
Wiring: both are kernel defaults — the your-project pack inherits them automatically and ships no custom subagents. Everything else (epic + reference enrichment, per-task exploration, code review, blast radius) runs inline in the agent that needs it. A pack can add its own delegated workers at extension points (surgeon_pre_task, surgeon_post_task, review_post_check) via subagents: in pipeline.<pack>.yaml.
Guardrails

Rules, skills & subagents

Three different trigger models: rules are injected into every run automatically; skills load only when a task needs them; subagents are called at specific points. The firing map below shows exactly when and where each one kicks in across the pipeline.

Always-on rules (Tier 1 · agent-flow.mdc + pack rules)

  • Build safety — builds.forbidden blocks *deploy*, db drop/truncate, git push --force* before every command.
  • Git ownership — only Ship commits, pushes, or opens PRs. Surgeon writes code, never git.
  • No hallucinated paths — every file is ls-verified before it's referenced.
  • Never silently skip — missing content prompts a fallback gate; it never guesses or crashes.

On-demand skills (Tier 2 · declared in YAML)

SkillLoads when
layer_map[<layer>].skillsSurgeon touches a file matching that layer — per task
orchestrator.lld_generatorOrchestrator Phase B (LLD synthesis) — once per run
orchestrator.ticket_schema_storyOrchestrator parses the ticket into the schema
Add a skill in 3 steps: write the .md under packs/<pack>/skills/ → reference it in layer_map → npm run install-pipeline -- --pack <pack> --merge-config. Rules are simpler: drop the .mdc in packs/<pack>/rules/ (always Tier 1) and re-install — no YAML wiring.

Setup

One-time setup order (tech lead)

Run once per project. The pipeline config must be installed before Work on <story> will start — after this, developers just run tickets with no per-ticket config step.

1. npm run install-pipeline -- --project-root /path   # splits the pack into 5 config files
2. set the core keys (table below)
3. node contexts/tools/validate.mjs                   # expects 10 checks
4. @project-analyzer.md Analyze project               # auto-fills shared_paths, layer_map, i18n…
5. @orchestrator.md Work on JIRSTORY-1234             # first ticket

Install writes 5 split files to contexts/config/ — edit them directly and commit them:

FileSet before first ticket
pipeline.<pack>.yaml (core)meta.pack (must match filename stem) · runtime.branching.base_branch · jira.project_key · mcp_servers / mcp_roles
pipeline.<pack>.skills.yamlskills.layer_map — so Surgeon loads the right layer standards
pipeline.<pack>.builds.yamlbuilds.commands + builds.forbidden (build + safety denylist)
pipeline.<pack>.analyzer.yamlmostly auto-written by project-analyzer — leave it
pipeline.<pack>.e2e.test.yamldemo.* — optional, only if you use AC-E2E-Check
Config changes are committed like code: edit a split file, run validate.mjs, commit, teammates git pull. Running --offline lets you skip the MCP keys and feed the ticket via contexts/ticket-input.md instead.
Troubleshoot

When something surprises you

Debugging order: read the agent prompt → read the skill it loaded (shown in the Active Context block) → read the config section it used. The answer is always in one of those three.

SymptomFix
No context file found for JIRSTORY-1234A downstream agent ran first. Start with @orchestrator.md Work on JIRSTORY-1234.
Ambiguous context fileSame ticket ID in two folders. Move one to contexts/archive/.
skill_loaded=<none — no config>A split YAML failed to parse. Run node contexts/tools/validate.mjs.
Plain trigger didn't run in CursorUse the @<agent>.md <trigger> form, or run it from Claude Code.
Review says "clean" but code looks brokenReview checks AC compliance + regressions, not behavioral correctness. The LLD may be wrong — amend from the top.
Ship does not support standalone modeBy design — Ship requires a Review. Use the full pipeline.
