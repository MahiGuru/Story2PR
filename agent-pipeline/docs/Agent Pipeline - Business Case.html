The problem

Where developer time goes today

Each story pulls a developer through the same motions: read the ticket, hunt the codebase, decide what to reuse, write code, run builds, raise the PR. Most of it is repeatable. Almost none of it is reused across stories or developers.

What costs us today

  • Project knowledge in senior heads. Each story rebuilds context from scratch.
  • Similar stories diverge. Two developers solve similar tickets in incompatible ways.
  • Generic AI tools don't know our stack. Off-the-shelf AI either ships without review or ignores conventions.
  • No audit trail. "Why was this built this way?" gets a 2-line commit message.
  • Onboarding takes weeks. New hires spend 2–3 weeks learning before shipping their first ticket.

What we want instead

  • Project knowledge captured once, applied consistently to every story.
  • Developer controls every step. AI does the repeatable work; human approves at every gate.
  • A written record at every stage — committed alongside the code.
  • Predictable cost. Same agents, same context slices, every time. No growth.
  • Fast onboarding. New hires productive in days, not weeks.
The solution

A guided AI pipeline — developer approves every stage

Five specialized AI agents collaborate through a staged flow. Each has one job, reads the previous stage's output from a file, produces its own artifact, and waits for the developer's approval before the next stage runs.

Specialized agents

Five agents, one narrow role each — Orchestrator plans, Explorer scans the codebase, Surgeon implements, Review verifies, Ship opens the PR. Focused agents produce focused output, not generic AI guesses.

Developer-gated

Five approval gates, one per stage. The developer reviews each artifact and types a short approval. Nothing runs autonomously for hours.

Auditable by default

Every stage writes its work to a file committed in the PR. Full audit trail for every story, searchable forever.

Project-aware

A one-time scan captures the project's components and conventions. Every story benefits — the AI never sees the codebase as a stranger.

Where the savings come from — epic context

One file does most of the work — epic-context.md. As stories ship, each one writes a compact ~300-token summary of what it built, decided, and constrained. The next story's agent reads that ledger instead of re-loading every prior story's full design. Same knowledge, ~10× cheaper to access — and the savings compound the longer the epic runs.

Without epic context (chat-based AI)

Every story re-pastes the design doc, sibling story LLDs, and acceptance criteria into the conversation. By story 10, the agent is reading ~500K tokens of redundant history just to start work. By story 15, it's burst past 1M.

With epic context (the pipeline)

The agent reads epic-context.md once — every prior story summarized in one compact ledger. Plus the cached codebase map and the epic HLD reference. ~80K tokens total, regardless of where in the epic you are.

Epic context — helps the team, not just the AI

For the team

  • Living memory of the epic. What every prior story decided, built, and reused — captured in one file the team can read.
  • New developer onboarding. Read epic-context to understand the epic's history. No tribal-knowledge transfer needed.
  • Fewer regressions. Story 8 sees story 7's choices before any code is written — no accidental conflict with prior work.
  • Audit trail by default. Post-mortems get primary-source material — every story's design, every decision, in one place.

For the AI agents

  • Epic HLD auto-cached. The architecture decisions for the epic are read once, then referenced — not re-fetched per story.
  • Sibling stories as 300-token summaries. Replaces re-reading 3K-token full LLDs. Cost flat instead of growing.
  • Drift detection. If a sibling story shipped via a regular PR (not the pipeline), the agent auto-fetches its summary into epic-context.
  • Reuse confidence. Agent knows what already exists in the codebase, so it picks reuse over recreation.
For grounding (the only money mention in this brief): at typical 40-stories-per-developer-per-month workload, the pipeline costs roughly the equivalent of one hour of senior developer salary per developer per month. How to use

Story → PR in one command. Every gate is yours.

Each stage runs a specialized agent and ends at an approval gate. The developer reviews the artifact, types a short approval (or Amend: <change>), and proceeds to the next stage. No agent runs without explicit authorization.

One short command kicks off the entire pipeline. The developer types Work on PROJ-1234 and the pipeline begins. From that point on, every action is just a short approval at each gate — no other commands to memorize, no flags to pass, no config to manage per story.

Amend at any gate

Type Amend: <your change> instead of Go. The agent revises that section only — it doesn't re-run the entire stage. ~70% cheaper than re-running.

Branch flexibility (Stage 1)

Go creates from develop. Go, stack stacks on your current feature branch. Go, from <branch> uses any base. Choice surfaced automatically when stacking is detected.

Resume tomorrow

Type Cancel, close the laptop, come back any day. Re-run the next stage's command — the pipeline picks up from the last approved gate. No re-explaining.

Most gates are a single-word approval. Out of the ~7–9 gates per story, most fire only when there's something to decide. Build-failure gates only appear if a build fails. Stack-vs-base gates only appear when the developer is on a feature branch. The "happy path" is mostly typing Go.

Cross-cutting capabilities — apply across all stages
▸ Amend at any gate. Type Amend: <change> instead of Go. The Amender subagent makes targeted section edits — ~70% cheaper than re-running the full agent.
▸ Inline context fallback. When MCP integrations are unreachable, agents fall back to local files (contexts/ticket-input.md, inline Context: blocks in the trigger) and --offline mode. Pipeline still runs end to end.
▸ Resume from anywhere. Every agent's output is a file. Cancel any time, come back any day, re-run the next stage's command — pipeline picks up from the last approved gate. No reconstructing context from chat history.
▸ Standalone mode. Quick fixes that don't need a JIRA ticket can run a single agent directly (no full pipeline). Same agents, single-stage invocation.

How it helps

How it helps — developers and managers

The same system delivers different value to different audiences. Developers gain time and clarity; managers gain consistency and predictability.

For developers

  • ~3–6 hours of coding becomes ~90 min of reviewing Active typing time on a medium story drops dramatically; the developer reviews and approves instead of hunting and typing.
  • Less codebase hunting The Explorer agent finds insertion points and reuse candidates automatically. No more "where does this go?".
  • Standards applied automatically Naming, file placement, accessibility, security — applied without thinking, on every story.
  • Resilient to interruptions Multi-day stories, sick days, laptop reboots — work resumes from files. No reconstruction from chat history.
  • Onboarding in days, not weeks The project catalog captures the tribal knowledge that usually takes 2–3 weeks. New hires ship a real ticket on day 2.
  • Faster code reviews Every PR arrives with the design, exploration, change manifest, and verdict already attached. Reviewers focus on judgment, not investigation.

For management

  • Predictable cost per story Cost stays flat as the epic grows. Forecasting is straightforward; no surprise bills at quarter-end.
  • Consistent quality across the team The same standards apply on every ticket by every developer. Junior and senior developers ship code that looks the same.
  • Higher throughput, same headcount More stories per sprint without adding people. Developer time shifts from mechanical work to judgment.
  • Complete audit trail Design, exploration, manifest, review verdict — all files in the PR. Post-mortems get primary-source material.
  • Lower regression risk Full build + test suite gate every PR. A failed verdict halts shipping; broken code never reaches reviewers.
  • Vendor-neutral Runs in Cursor or Claude Code — both subscription tools the team already has. Zero lock-in to either vendor.
What runs at each stage

Five stages — each agent has one job

Each stage produces a named artifact, a clear next step, and a short approval prompt. The developer sees what the agent is about to do before it does it.

Stage 1 · Plan
Orchestrator
Reads the ticket and the full epic context (HLD, sibling stories, codebase map). Produces a requirement summary, AC registry, and low-level design with a clear task breakdown. Identifies what to reuse from existing code.
Stage 2 · Explore
Explorer
Scans the codebase for the exact insertion points named in the design. Confirms reuse candidates with file paths and line numbers. Flags duplicates before they're created.
Stage 3 · Implement
Surgeon
Writes code one task at a time. Runs lint and unit tests after each task. Runs the full build at the end. Maintains a change manifest.
Stage 4 · Review
Review
Runs the full test suite. Checks every acceptance criterion. Calculates blast radius. Produces a ship-or-fix verdict with evidence — committed alongside the code.
Stage 5 · Ship
Ship
Verifies all build verdicts are PASS. Commits the work. Opens the PR with the design, manifest, and verdicts attached. Updates the JIRA ticket.

Decision & rollout

The decision — three weeks to full adoption

We're asking for approval on a small, time-boxed pilot. The investment is bounded; the risk is low; the upside is measurable within two weeks. Below: what we're asking for, then the rollout plan if approved.

What we're asking management to approve

  • Pilot scope: 3 developers × 5 stories each over 2 weeks. Tracked in standard sprint cadence.
  • Tech-lead time: ~4 hours one-time to install and run the project analyzer.
  • Pilot developer time: ~30 minutes onboarding each. Their actual story work proceeds on the pilot.
  • Subscription cost: none — uses the same Cursor / Claude Code subscriptions developers already have.
  • Success criteria: at the end of 2 weeks, we measure (a) cycle time per story, (b) defect rate at PR review, (c) developer satisfaction. Positive results → expand to full team in week 3.
  • Rollback risk: low. Opt-in per developer and per ticket. Any developer can step out at any time and continue with their existing flow.

Rollout plan if approved

The pipeline is opt-in per developer and reversible at any stage. The recommended rollout staggers risk — small pilot first, then team-wide.

Week 0 · Setup (one-time)

Tech lead installs the pipeline + pack

~1 hour of installation. The project analyzer runs once to generate the project catalog. Catalog committed to the repo so every developer inherits it.

Week 1 · Pilot

Three developers, five stories each

Three volunteer developers run their next 5 stories through the pipeline. Daily check-in on what's working. Cost is bounded and small.

Week 2 · Review + adjust

Pilot retrospective, pack refinements

Pilot team shares findings. Any pack rules that need tuning are folded in. Re-tested on the next ticket — pack improves continuously, agents stay the same.

Week 3 · Team-wide

Pipeline becomes the default

Remaining developers onboarded. Each gets a 30-minute walkthrough from a pilot developer. From this point forward, the pipeline is the team's standard story-delivery flow.

~83% lower cost. ~3–6 hours saved per medium story. 0 PRs shipped without human approval.
If the pilot results match the projections, this becomes one of the highest-ROI tooling investments we make this year — measured in hours of senior developer time saved per week.
Honest caveats. The numbers in this brief are modeled on representative medium stories. Actual savings depend on story shape, story count, and how consistently the team adopts the gates. Expect 70–90% of the quoted savings in real-world use; the pilot exists to validate.
