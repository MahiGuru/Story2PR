Big picture

Kernel + Pack → Installer → Host output

The kernel is a project-neutral agent prompt set + always-on flow rules. The pack is project-specific knowledge: LLD generator, layer coding standards, ticket schemas, naming/placement rules, and the pipeline.<pack>.yaml seed. The installer composes them and writes a host-specific output (.cursor/ or .claude/) plus a host-agnostic contexts/ tree.

kernel + pack architecture · authoring → install → host output

Mental model

  • Kernel = the agent prompts + cross-agent flow rule. What every project shares.
  • Pack = your stack's standards + LLD generator + layer skills + naming rules. What makes the kernel actually run on YOUR codebase.
  • Installer = composer. Reads kernel + pack, writes host-targeted output to your project.
  • Host = Cursor or Claude Code. The same agents + skills, packaged differently.
Pack tree

Authoring

How to extend a pack

Three things you typically add: a new skill (per-layer or new domain), a new always-on rule, or a new subagent at one of the kernel extension points. After every change run validate.mjs.

Add a new layer skill

# 1. Create the skill file
packs/myproj/skills/myproj-mynewlayer-standards.md

   ---
   name: myproj-mynewlayer-standards
   description: Coding standards for <layer description>
   ---
   # <Layer> Standards
   ... your standards content ...

# 2. Wire it into the layer_map (split file is preferred over seed)
contexts/config/pipeline.myproj.skills.yaml:

   skills:
     layer_map:
       Frontend/MyNewLayer:
         path_glob: "src/web/mynewlayer/**/*.ts"
         aliases: [mynewlayer, my-new-layer, MNL]
         skills: [myproj-mynewlayer-standards]
         build: build-mynewlayer

# 3. Validate (regenerates _catalog.md)
node contexts/tools/validate.mjs --update-catalog

# 4. Commit the skill, the YAML edit, and the new _catalog.md

Add a new always-on rule

# 1. Create the rule (Cursor format)
packs/myproj/rules/myproj-myrule.mdc

   ---
   description: One-line summary
   alwaysApply: true
   ---
   # Rule body
   ... rule content ...

# 2. Re-install to copy it into the host folder
npm run install-pipeline:cursor   # or :claude
# Installer copies it to .cursor/rules/myproj-myrule.mdc
# (or .claude/rules/myproj-myrule.md — alwaysApply stripped)

# 3. Validate
node contexts/tools/validate.mjs

Add a new subagent (kernel extension point)

# 1. Create the subagent prompt
packs/myproj/agents/subagent-myproj-security-scan.md

   ---
   name: myproj-security-scan
   description: Pack subagent fired at surgeon_post_task to scan for secrets / PII
   ---
   # Body: instructions, return verbs, contract...

# 2. Wire it at the extension point in the seed
packs/myproj/pipeline.myproj.yaml (or contexts/config/pipeline.myproj.yaml core):

   subagents:
     surgeon_post_task:
       - name: myproj-security-scan
         agent: subagent-myproj-security-scan
         when: "task touches src/web/** OR task touches src/api/**"

# 3. Re-install + validate
npm run install-pipeline
node contexts/tools/validate.mjs

Four extension points (kernel-defined)

Extension pointFires whenUseful for
orchestrator_amend_requestUser types Amend: at Orchestrator's Phase C gateKernel ships Amender here. Packs can replace.
surgeon_pre_taskSurgeon, after layer resolution, before code changePre-implementation security audits, dependency checks, scope-drift warnings
surgeon_post_taskSurgeon, after per-task lint + tests passLightweight code review, snapshot tests, performance gates
review_post_checkReview, after AC compliance checkLicense scans, accessibility audits, secrets scans
Skill vs subagent — when to use which. Use a skill when the work IS the parent agent's job (LLD generation, applying coding standards) and the inputs already live in the parent's context. Use a subagent when the work has heavy intermediate data the parent doesn't need (image analysis, audit scans) and a small structured return is enough.

Install command

npm run install-pipeline — full reference

One command, many flags. Sensible defaults: --target cursor, --pack myproj, validates after install, generates MCP sample.

Most common usage

# Fresh install — Cursor target, myproj pack
npm run install-pipeline -- --project-root /path/to/your/project

# Claude Code target
npm run install-pipeline:claude -- --project-root /path/to/your/project

# Different pack
npm run install-pipeline -- --project-root /path/to/project --pack mypack

# Both hosts on the same project (run twice)
npm run install-pipeline:cursor -- --project-root /path/to/project --pack myproj
npm run install-pipeline:claude -- --project-root /path/to/project --pack myproj

All flags

FlagDefaultBehavior
--project-root <path>—Target project directory (required for live install)
--target <cursor|claude>cursorWhich host folder to write (.cursor/ or .claude/)
--pack <name>myprojWhich pack to install from packs/
--no-pack—Kernel-only install — skips pack content
--output-dir <path>—Staging mode — build to a directory instead of live install
--force-config—Overwrite contexts/config/pipeline.*.yaml from pack seed (backs up existing to .bak.<timestamp>)
--merge-config—Section-aware merge: pack-owned sections take new content; analyzer-owned (shared_paths, operation_patterns) preserve dev's edits
--no-mcp—Skip MCP sample generation
--no-validate—Skip validator run after install
--dry-run—Print what would happen, write nothing
--with-handoff-hook—Claude Code only — install Stop hook (clipboard + desktop notification on agent finish)

What happens during install (in order)

  1. Read sources — scan agent-pipeline/ (kernel) + packs/<name>/ (pack)
  2. Compose — merge agent prompts, rules, skills
  3. Transform per host — Cursor keeps .mdc + alwaysApply; Claude renames to .md, strips alwaysApply, packages skills as <name>/SKILL.md
  4. Copy to project — write .cursor/ or .claude/ in --project-root
  5. Split config — read packs/<name>/pipeline.<name>.yaml seed, split into 5 sibling YAMLs at contexts/config/
  6. Copy project-context.<name>.md → contexts/project-context.md
  7. Copy project-input.template.md → contexts/ticket-input.md
  8. Generate MCP sample (skip with --no-mcp)
  9. Validate (skip with --no-validate)

Validator (no script alias — run directly)

node contexts/tools/validate.mjs                  # 10 checks · prints report
node contexts/tools/validate.mjs --update-catalog # also regenerate _catalog.md
node contexts/tools/validate.mjs --quiet          # CI mode (silent on success)

Why no npm install? The tools vendor their one dependency (js-yaml) at contexts/tools/vendor/js-yaml.mjs. Run them with node directly — they work in any project that has Node 18+. The package.json's dependencies field exists for the pipeline-release repo itself, not for the projects that install the pipeline.

Validate

The 10 checks

node contexts/tools/validate.mjs runs three tiers of checks. Auto-discovers config files at contexts/config/ (supports both monolithic and split layouts). Exit codes: 0 = pass, 1 = errors, 2 = environment problem.

TierCheckWhat it catches
1Schema versionPipeline schema mismatch with installer version
1YAML parseIndentation / syntax errors in any of the 5 split files
1Section collisionsSame top-level key declared in multiple split files (e.g. skills in both core + skills.yaml)
2Layer resolutionEvery layer in skills.layer_map resolves correctly via path_glob + aliases
2Alias collisionsTwo layers declaring overlapping aliases (Surgeon would resolve ambiguously)
2Build command referencesLayers reference build commands that exist in builds.commands
3Skill file existenceEvery skill referenced in config (LLD generator, layer skills, bug-localization, etc.) exists in .cursor/skills/ or .claude/skills/
3Rule file existenceEvery rule file in rules/ is properly formatted
3Agent file existenceEvery agent referenced in subagents.* exists in agents/
3Retired MCP fields deprecationWarns if any mcp_servers.* entry still has the retired fields (used_by, required, skip, fallback_prompt) — routing now lives in mcp_roles; skip is via CLI flags

Catalog

The validator can regenerate contexts/config/_catalog.md — a human-readable table of every canonical layer, its aliases, the path_glob, the skills it loads, and the build command. Always in sync with what the resolver actually does. Regenerate after any skills.layer_map edit:

node contexts/tools/validate.mjs --update-catalog
MCP setup

Connect Atlassian, GitHub, Figma

The installer writes a starter MCP config at contexts/config/mcp.sample.json + mcp.sample.README.md with per-host setup instructions. Each developer copies entries into their personal MCP config (Cursor or Claude Code).

MCPAuthUsed byRequired?
Atlassian (JIRA + Confluence)OAuth (browser-based)Orchestrator (ticket fetch + reference auto-discovery), Review (pattern check), Ship (transitions)Recommended — fall back to --offline + ticket-input.md
GitHubPersonal access token (repo scope)Orchestrator (PR status), Explorer (multi-repo), Review (reference PR pattern), Ship (PR creation)Recommended for Ship
FigmaPersonal access tokenOrchestrator (frame fetch from URLs)Optional — falls back to drag-drop image attachment

Graceful fallback when MCPs are unavailable

# Use only specific MCPs (skip the rest)
@orchestrator.md Work on PROJ-1234 --only github

# Skip specific MCPs
@orchestrator.md Work on PROJ-1234 --skip atlassian,figma

# Fully offline (no MCPs at all)
@orchestrator.md Work on PROJ-1234 --offline
# Reads contexts/ticket-input.md as ticket source
MCP failure = inline gate, not a failed run. If an MCP is configured but probe fails at runtime, Orchestrator opens a gate: retry / inline / file / skip / cancel. You handle the fallback in the same conversation — no need to abort and re-trigger.

mcp_roles — rewire MCPs without kernel changes

Every MCP-consuming agent (Orchestrator, Review, Ship, AC-E2E-Check) resolves four mandatory roles to concrete MCPs at pre-flight. Teams swap Atlassian → Linear or GitHub → Bitbucket by editing one config block — no prompt changes.

RolePurposeDefault MCP (shipped pack)
story_sourceFetch ticket body + ACs, transition status on PR openatlassian (JIRA)
design_sourceFetch design frames / visual specsfigma
vcsBranch, commit, PR creation, reference-PR diff fetchgithub
docs_sourceFetch HLDs, wiki pages, requirements docsatlassian (Confluence)

Value shapes per role

ValueMeaningGate behavior when content needed
atlassianSingle primary MCPFires only if probe fails
[github, bitbucket]Primary + ordered fallback listFires only if all candidates fail probe
null or []Config-time skip — equivalent to passing --skip for this role every run. Pack declares "never use an MCP for this role."Fires on demand — if the ticket needs the role's content (e.g. Figma URLs present + no attachments), user is prompted for an alternative (upload image, fill ticket-input.md, paste inline Context:). If content isn't needed this run, stays silent.
(key missing entirely)Validator error — mandatory role missing. Forces an explicit decision: pick an MCP or opt out with null.n/a (blocks install)
Why null still prompts: setting design_source: null doesn't mean "design is irrelevant" — it means "never call the design MCP." If a ticket then shows up with Figma URLs but no attached images, the agent still needs a design input; it prompts you to upload one instead of silently skipping. Same rule applies to all four roles.

When does the gate actually fire? — per role

The gate is "role has no MCP AND the ticket actually needs its content." Each role has a specific content-dependency check, so backend-only or DB-only tickets don't get prompted for design input they'll never use.

RoleGate fires when all of these are true
story_sourceNo contexts/ticket-input.md AND no inline Context: in trigger
design_sourceTicket has Figma/design URLs · AND no image attachments in trigger · AND scope.ui_involved == true
docs_sourceTicket references HLD/wiki pages AND no local doc file provided
vcsA reference ticket is declared AND its PR diff is requested

Concrete scenarios — design_source: null

Your ticketWhat happens
Backend / DB change · no Figma URLs · no imagesSilent. scope.ui_involved = false short-circuits the check. Active Context notes: "design_source not needed this ticket."
UI ticket · Figma URLs in description · no images attachedGate fires. "design_source is skipped (config). Provide design via: upload image / cancel."
Any ticket · image attached (flow diagram, sequence diagram, whiteboard sketch, UI mock, screenshot, architecture diagram)Silent. The attachment satisfies the content requirement. The image-analysis subagent extracts whatever structure it finds (boxes+arrows for a flow diagram, component tree for a UI mock) and hands it to downstream agents as context.
Any image type works. The kernel doesn't classify images — it extracts whatever structure is in them. Flow diagrams, sequence diagrams, whiteboard sketches, screenshots, architecture diagrams all count equally as "design input provided." Your ticket prose is what interprets them. So a backend ticket with a flow diagram attached won't be mistreated as "UI to implement" — the flow becomes supplementary context for the LLD.
Scope classification is automatic but overridable. scope.ui_involved is set by a cheap LLM pass (classify_scope (A0.6.3)) over the ticket title + description. Signals like "screen", "page", "button", "modal", "Figma" → UI-involved; "DAO", "migration", "REST endpoint", "batch job", "schema" → not UI-involved. If the classifier gets it wrong, override at the Phase C gate with Amend: scope.ui_involved = true (or false).

mcp_roles:
  story_source: atlassian
  design_source: null            # never uses designs
  vcs: [github]

Resolution ladder (per role, per run)

1. Flags win first: --offline / --skip <name> / --only <list>
2. Walk mcp_roles.<role> → first candidate still allowed after step 1
3. Consult mcp_guidance.<role> for declared quirks (e.g. "ODO- prefix → odoo")
4. Check the candidate MCP is reachable at the host · else try next fallback
5. No candidate left?
     flag explains it → local fallback (ticket-input.md / attachments / CLI git)
     no flag          → HALT with a clear per-role error message

Worked example — swap GitHub for Bitbucket

# 1. Declare the MCP
mcp_servers:
  bitbucket:
    auth: token
    config: { command: "npx", args: ["-y", "mcp-server-bitbucket"], env: { BITBUCKET_TOKEN: "${BITBUCKET_TOKEN}" } }

# 2. Wire the role — single source change
mcp_roles:
  vcs: [bitbucket, github]       # bitbucket primary, fall back to github

# 3. (Optional) add a guidance quirk
mcp_guidance:
  vcs: |
    If the repo URL is on bitbucket.org, always prefer bitbucket MCP
    regardless of fallback order.

# 4. Validate + re-install + each developer adds Bitbucket token to their
#    personal Cursor / Claude Code MCP config.
What the validator enforces: all four mcp_roles keys mandatory · every value references a real mcp_servers key (or is null / [] for explicit opt-out) · orphan guidance keys warned · legacy per-server fields (used_by, required, skip, fallback_prompt) are retired and produce deprecation warnings if still present.

mcp_servers — slim developer-onboarding registry

After the mcp_roles routing landed, mcp_servers was reduced to its original purpose: generating contexts/config/mcp.sample.json for new-developer setup. Three fields per server, nothing else:

mcp_servers:
  atlassian:
    auth: oauth                    # oauth | token | token_or_oauth
    config:                        # connection — source for mcp.sample.json
      url: "https://mcp.atlassian.com/v1/mcp"
    setup_hint: |                  # pack-author notes for new developers
      On first run, browser opens for Atlassian login.
      Your org admin must have Atlassian Rovo MCP Server enabled.

  github:
    auth: token
    config:
      command: "npx"
      args: ["-y", "@modelcontextprotocol/server-github"]
      env:
        GITHUB_TOKEN: "${GITHUB_TOKEN}"
    setup_hint: |
      Create a PAT with 'repo' scope at github.com/settings/tokens.

What was retired from mcp_servers

Retired fieldReplaced by
used_by: [...]mcp_roles — routing is role-based, not server-based
required: trueFallback chain — a role halts only if no candidate resolves AND no flag explains it
skip: trueCLI flags (--skip <name>) for per-run opt-out, or mcp_roles.<role>: null for config-time opt-out
fallback_prompt: ...Built-in per-role gate text. Packs that need different wording override at the rule layer (.cursor/rules/*.mdc), not in pipeline.yaml.
Legacy packs keep working. If your pack still has the retired fields, the validator warns (not errors) and the fields are ignored. Routing now always comes from mcp_roles. Safe to strip at leisure.
What's abstracted, what's not. The routing decision (which MCP handles which role) is fully config-driven. The concrete CLI / API calls are still hardcoded in agent prompts — for example, Ship's PR-create step uses gh (GitHub CLI). Swapping vcs to Bitbucket works for pre-flight resolution + status display, but the PR-create command itself needs a pack-specific override (install glab / bitbucket CLI and override the Ship step in a pack rule file). This is honest scope — future PRs can abstract over VCS operations via the resolved MCP's actions.
Upgrade flow

Re-installing for upgrades

When a new pipeline release ships, re-run the installer. Section ownership in the split YAMLs determines what gets replaced and what's preserved.

Standard upgrade (preserves your config)

# Re-run the installer in the new release folder
npm run install-pipeline -- --project-root /path/to/project --pack myproj --merge-config

# Behavior:
# - .cursor/ (or .claude/) agents, rules, skills → REPLACED
# - contexts/config/pipeline.*.yaml → MERGED (section-aware)
#   * skills.* / builds.* / jira.* / subagents.*  → take new pack version
#   * shared_paths, operation_patterns, i18n, component_naming → KEPT (your edits + analyzer's auto-fills)
#   * runtime.* / mcp_servers.* → KEPT (your customizations)
# - contexts/project-map.md → UNCHANGED (your project's catalog)
# - contexts/project-context.md → UNCHANGED (your team's prose)
# - contexts/<epic>/* → UNCHANGED (your runtime data)

Force-overwrite upgrade (rare)

npm run install-pipeline -- --project-root /path/to/project --pack myproj --force-config

# Behavior:
# - All split YAMLs OVERWRITTEN from the new pack seed
# - Existing splits backed up to .bak.<timestamp>
# - You'll lose project-analyzer-written sections — re-run @project-analyzer.md after

Section ownership reference

SectionOwnerBehavior on --merge-config
skills.layer_map · skills.orchestrator · skills.explorerPack authorReplaced
builds.commands · builds.runner · builds.review_gatePack authorReplaced
jira.* · mcp_servers.* defaultsPack authorReplaced (then you re-customize)
subagents.*Pack authorReplaced
shared_paths · component_naming · operation_patterns · i18nProject AnalyzerPreserved
runtime.contexts_layout · runtime.branchingYouPreserved
Upgrade workflow: commit your contexts/config/ splits before re-installing. After install, run git diff contexts/config/ to see what changed and merge any conflicts manually if needed. Then run node contexts/tools/validate.mjs to confirm.
Daily use

Using the pipeline in your project

Once installed and analyzed, the daily-driver flow is six commands. Tech lead does the one-time setup; team members run tickets.

One-time setup (tech lead)

# 1. Install
npm run install-pipeline -- --project-root /path/to/project --pack myproj

# 2. Validate
node contexts/tools/validate.mjs

# 3. Analyze the project (Step 0)
@project-analyzer.md Analyze project
# Takes 5-15 min · produces contexts/project-map.md + auto-fills 5 split YAMLs

# 4. Edit contexts/project-context.md with team-specific prose

# 5. Commit project-map.md, project-context.md, and contexts/config/*.yaml to your repo

# 6. Each developer:
#    - Pulls the repo
#    - Sets up their personal MCP config (see contexts/config/mcp.sample.README.md)
#    - Starts running tickets

Per-ticket flow (every developer)

@orchestrator.md Work on PROJ-1234       # Phase C gate: Amend / Go / Cancel
@explorer.md Run the explorer            # gate
@surgeon.md Run the surgeon              # gate
@ac-e2e-check.md Demo PROJ-1234          # OPTIONAL — browser AC verification
@review.md Run the review                # gate
@ship.md Ship it                          # commit + PR + JIRA

Standalone (no ticket)

@explorer.md Research: how does X work?
@surgeon.md Apply: <spec> in <files>     # ≤5 files / ≤150 lines
@review.md Review changes
@ac-e2e-check.md Demo <URL>
