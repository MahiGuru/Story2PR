Overview

Two folders, two loading patterns

After install, your project has two new top-level folders to know about: .cursor/ (Cursor reads agents, rules, skills from here) and contexts/ (host-agnostic runtime data, configuration, tools). Inside .cursor/, two loading patterns matter — rules are always-on (injected into every agent run automatically), skills are on-demand (loaded by an agent only when it needs them).

.cursor/ + contexts/ · always-on rules + on-demand skills
Two loading patterns to remember:
(1) Rules in .cursor/rules/ are always-on. The alwaysApply: true frontmatter tells Cursor to inject every rule file into every agent run, automatically. You don't choose which rules apply — they all do, every time.
(2) Skills in .cursor/skills/ are on-demand. Each agent's pre-flight resolves which skills it needs (from contexts/config/pipeline.<pack>.skills.yaml) and reads them — Orchestrator loads the LLD generator only at Phase B; Surgeon loads layer skills per-task; Explorer loads bug skills only in Bug Mode.

9 agents

Same agent set whatever host you install to. Cursor invokes them with @<name>.md <trigger>. Plain triggers route via agent-flow.mdc but can be flaky.

Rules format

Cursor uses .mdc with frontmatter. alwaysApply: true tells Cursor to inject the rule into every agent run — that's how kernel + pack standards reach every agent.

Skills loading

Skills are flat .md files. Agents read them on demand (Orchestrator's LLD-generator at Phase B; Surgeon's layer skills per task; Explorer's bug-localization in Bug Mode).

Example — offline trigger with local content

# 1. Edit the input file ONCE

# Fill: title, summary, ACs, in/out of scope

# 2. Drag 1-3 design screenshots into the Cursor chat

# 3. Trigger with --offline

# Orchestrator reads ticket-input.md + attached images · no network calls
# Saves ~15-40K tokens vs full MCP run

# → Orchestrator reads ticket-input.md; still uses Figma + GitHub MCPs

MCPs at runtime

How agents use MCPs — and what happens when they fail

Three MCP servers extend the pipeline's reach: Atlassian (JIRA + Confluence), GitHub, and Figma. Agents consume them at specific pre-flight phases. All three are optional — every agent has a graceful fallback. For how to initially connect each MCP to your IDE, see the Packs & Install doc's MCP section.

What each MCP unlocks per agent

MCPUsed byAuto-discovers / fetches at runtime
Atlassian
(JIRA + Confluence)		Orchestrator · Review · ShipOrchestrator: fetches the JIRA ticket + Confluence HLD + sibling LLDs; auto-discovers reference tickets via jira.reference_link_types; fetches JIRA image attachments.
Review: pattern comparison against reference ticket's LLD.
Ship: JIRA transitions on PR open (e.g. In Progress → In Review).
GitHubOrchestrator · Explorer · Review · ShipOrchestrator: inspects reference ticket's PR status (merged / open / closed).

Review: fetches reference ticket's merged PR diff for pattern fidelity comparison.

Graceful fallback — what happens when an MCP isn't available

SetupBehavior
No MCPs configured, no explicit triggerStandard pipeline unchanged. Uses local files only (ticket-input.md, prose context). Requires full local content upfront.
MCPs configured, no explicit flagAuto-discovered enrichment flows through all 5 phases. Orchestrator probes each MCP; uses whatever responds healthy.
MCPs configured, explicit --skip / --offlineRespected — specific MCPs skipped. Fallback sources used (file + inline + images).
MCP probe succeeds but runtime call fails mid-wayInline recovery gate fires (see below) — no re-trigger needed.
Reference ticket pack mismatchWarn + proceed without the reference. Pipeline never halts over enrichment.

MCP failure → inline recovery gate

If an MCP probe succeeds at pre-flight but the runtime call fails (OAuth token expired, network timeout, rate-limited, server down), Orchestrator opens a gate in the same conversation. You answer it inline — no need to abort and re-trigger.

Atlassian failure

⚠ Atlassian MCP failed to connect — OAuth token expired (403 Unauthorized)

JIRA ticket content for PROJ-1234 can't be fetched automatically. Pick one:

  1. retry    — Try connecting again (fix your MCP token, then reply `retry`)
  2. inline   — Reply with "Context:" + ticket summary + ACs, I'll parse as JIRA
  3. file     — Fill contexts/ticket-input.md, then reply `continue`
  4. skip     — Proceed with whatever local content exists
  5. cancel   — Exit; re-trigger when MCP is back

> 👉 Pick one:

Figma failure

⚠ Figma MCP failed — network timeout
2 Figma URL(s) referenced in ticket can't be fetched.

Pick one:
  1. retry    — Try again
  2. upload   — Drag design image(s) into chat, reply `continue`
  3. skip     — Continue with URL-only Visual Spec (weaker Phase B biasing)
  4. cancel   — Exit

> 👉 Pick one:
Silent degradation — the gate does NOT fire when the failure is immaterial: Figma down but ticket has no Figma URLs; Atlassian down but ticket-input.md is pre-filled; GitHub down and no reference ticket declared. Orchestrator notes the skipped probe in the Active Context block and proceeds.

The Active Context block — what Orchestrator tells you about MCPs

Every Orchestrator pre-flight prints an Active Context block showing which MCPs were used, skipped, degraded, or recovered. Read it when something surprises you — it always reports what actually drove the run.

┌─ Active Context — Orchestrator ────────────────────────┐
│ Ticket:  PROJ-1234 · Story                             │
│ MCPs:    atlassian ✓ · github ✓ · figma ✗              │
│          figma degraded → using 2 uploaded images      │
│ Input:   JIRA ✓ · trigger attachments ✓ (2 images)     │
│ Skills:  myproj-ticket-schema-story ✓                  │
│          myproj-ac-templates-intent-aware ✓            │
│          myproj-lld-generator (Phase B only)           │
└────────────────────────────────────────────────────────┘

Status markers: ✓ healthy · ✗ failed/skipped · degraded → <recovery method> · skipped (<--flag or reason>). If you see → recovered via <method>, the failure gate fired and your fallback (inline / file / upload) was applied.

When to use a flag vs let the gate handle it

SituationRecommended approach
MCP works normally; you want to save tokens or keep content private--skip <name> upfront — cleaner, no gate
MCP typically works, occasionally flakesDefault trigger. When it flakes, answer the gate
MCP down for extended time (org-wide outage)--offline or --skip atlassian,figma to avoid gate-per-story
Content is sensitive; don't want MCP calls at allFill ticket-input.md, attach images, use --offline
Why this design: you don't have to predict MCP outages. Default triggers work most of the time. If something breaks, you handle it in the same conversation — no need to abort, re-configure, and re-trigger.

rules/ inventory

Rules — always loaded into every agent run

Every .mdc file in .cursor/rules/ with alwaysApply: true in its frontmatter is auto-injected by Cursor at the start of every agent invocation. You don't pick which rules apply — they all do, every time. The kernel ships one (agent-flow.mdc); the pack adds project-specific standards (naming, placement, imports, postverify per layer).

FileSourcePurpose
agent-flow.mdcKernelCross-agent rules: path resolution (Procedure B), companion file contracts, build report contract, gate behavior, mode detection
myproj-project-scope.mdcPack: myprojTech stack, repo boundary, allowed/forbidden build commands, ticket prefix (PROJ-XXXX), source paths
myproj-file-placement.mdcPack: myprojWhere new files go — shared vs feature, module registration, package structure
myproj-naming-conventions.mdcPack: myprojFile, class, method, variable, i18nMessages key naming rules
myproj-import-patterns.mdcPack: myprojImport / require / module registration patterns per layer (AngularJS / Angular18 / Java)
myproj-{java,angularjs,angular18}-postverify.mdcPack: myprojSurgeon post-build verification per layer — invariants Surgeon must check after each task
Format difference: in .cursor/rules/ these are .mdc with alwaysApply: true in frontmatter. In .claude/rules/ they're .md with that frontmatter stripped (Claude Code auto-loads all rules in the folder).
skills/ inventory

Skills — loaded on demand, only when needed

Skills in .cursor/skills/ are NOT auto-injected. Each agent's pre-flight resolves which skills it needs (from contexts/config/pipeline.<pack>.skills.yaml) and reads them into its own context — keeping the rest out. This is how the LLD generator stays out of every non-Orchestrator agent, why Surgeon only loads the layer skill matching the current task, and why Bug Mode skills don't pollute Story Mode runs.

contexts/config/ — 5 split YAMLs

Why split, and what each file owns

The pack ships one monolithic pipeline.<pack>.yaml seed. The installer splits it into 5 sibling files at contexts/config/ — each agent only loads the splits it needs. Per-agent token savings: ~10K each (Orchestrator skips builds.yaml, AC-E2E-Check skips skills.yaml, etc.).

pipeline.<pack>.builds.yamlbuilds.commands · builds.forbidden · builds.runner · builds.review_gate · builds.tests · builds.review_test_suite · component_structure · operation_patterns · i18nSurgeon, Review, AC-E2E-Check

Claude Code (also)

Same model in .claude/, just a different file format

Everything above describes the Cursor host. Claude Code works exactly the same way — same 9 agents, same always-on rules, same on-demand skills, same contexts/ folder. Only the file format / packaging differs in the host folder.

.claude/
├── agents/    ← byte-identical to .cursor/agents/ (host-agnostic prompts)
├── rules/     ← .md (renamed from .mdc) · alwaysApply: stripped
│              ↳ Claude Code auto-loads ALL rules in this folder — no frontmatter needed
└── skills/    ← <name>/SKILL.md (dir-per-skill, Claude Code packaging)
               ↳ same skill content as .cursor — just wrapped in a folder per skill

Both hosts on the same project

A project can have both .cursor/ and .claude/ at the same time — they're independent host folders. The shared contexts/ is identical for both:

your-project/
├── .cursor/    ← used when you work in Cursor
├── .claude/    ← used when you work in Claude Code
└── contexts/   ← shared by both — config + runtime data + tools
Mental model: everything in this doc — the 9 agents, always-on rules, on-demand skills, the contexts/ tree — applies to Claude Code unchanged. Just translate the file paths: .cursor/rules/<name>.mdc → .claude/rules/<name>.md, and .cursor/skills/<name>.md → .claude/skills/<name>/SKILL.md. The behavior is the same.

For how to install one or both hosts, see Agent Team — Packs & Install.
